Purpose

The Man_In_Grey tools are used to facilitate the controlled generation and installation of system configuration files, such as the files under /etc. These tools can be used, for example, to complete unprivileged account builds that require system configuration file changes, and to support programs that run from unprivileged accounts but, as a normal part of their operation, require configuration file changes.

With the Man_In_Grey approach, each set of one or more configuration files is the work product of an unprivileged configuration composer program. When the composer program runs, it places commands into a journal. Later, a journal interpreter running in privileged mode reads the journal, approves it, and then executes its commands. The set of journal commands is purposely limited to make such verification possible.

Nothing in this arrangement is particular to configuration files. Man_In_Grey is a general means for a program running as one account to compose changes that a program running as another account checks and then makes. Typically the first account is unprivileged and the second is root. The command language a journal is written in is chosen by the application, not by Man_In_Grey. Configuration files are the first use, and the server of AccountTree is the first application.

What Man_In_Grey provides
  1. The journal interface, journal_iface, through which a composer makes a journal.
  2. A structure for gating, checking and executing journals: a compiled gate that changes the account the work runs as, a guard that checks every command of a journal against constraints, and a general interpreter that executes the journal once the guard has found nothing wrong.

An application chooses its command language and its constraints. Man_In_Grey comes with one command language, a small file language used for testing and for configuration files.

The general method of filling in templates mixes data and control together: the content to be written, and the marks that say where to substitute. This method is therefore a form of in-band signaling. With in-band signaling, a content string can be identical to a control string, so data and control can alias, and there is no tight way to design the aliasing out. The typical workaround is to disallow control strings in the data, and to write each disallowed character as an escape sequence, where the escape is then itself control. Each level of nesting multiplies the escapes: an f-string that explains how to write f-strings escapes its braces, and a document about that f-string escapes them again.

Man_In_Grey signals out of band. A composer is a program, so the logic that forms the output is code, with loops, conditions and lookups, rather than marks embedded in the output. A command in the journal is a structure, and file content is carried in it as a byte string with its length. The journal interpreter never scans content for meaning, so content can hold anything, including text that looks like a journal, with no escaping. This is the same principle as an extent string, where the extent of the content travels beside it rather than being marked within it.

The journal is encoded in CBOR, whose strings are length-prefixed for the same reason. Decoding CBOR makes maps, lists, strings and bytes, and cannot run code, so a journal reaches the privileged side as data and nothing else. A composer remains free to use a template inside itself; that is the composer's choice, and the journal does not inherit its aliasing.

Symbols

A composer writes commands; it does not run them. So when a command produces a value, such as the file an open opens, the value does not exist while the composer runs. The journal interface returns a symbol in its place: a reference to the command that will produce the value. A later command names the symbol, and the journal interpreter, executing the commands in order, gives it the value the earlier command produced.

file = journal_iface.open("/etc/unbound" ,"unbound-US.conf" ,"replace_keep" ,"root" ,0o644) journal_iface.write(file ,"server:\n verbosity: 1\n")

Here file is a symbol. In the journal it is the index of the open command, written {"symbol": 0}. A journal has no variables beyond this: a symbol is set once, by the command that produces it, and only later commands name it, which the journal interpreter checks before executing anything.

Constraints and the guard

Accounts exist to limit what programs can do. Man_In_Grey keeps those limits while letting a program running as one account ask for work done as another: the bespoke journal interpreter runs as the interpreter account, and its guard decides, by its constraints, which of the requested work is allowed. Because the guard runs before execution, it filters rather than audits after the fact.

The command language declares what can be done; the constraints declare where; the composer chooses among what the constraints allow. In the file language the composer names the file it opens, which keeps the composer readable, and the guard refuses any file the constraints do not list. Every later command about the file names its symbol rather than a path, so the constraints are checked once, at open.

Three rules make the guard dependable:

  • Check the whole journal, then execute. Every command is checked before the first is executed, so a journal that breaks a constraint anywhere changes nothing.
  • Keep the command language small. Each command is a narrow operation whose effect can be stated, so the guard can decide about it. A command such as "run this shell line" could not be checked, and belongs in no command language.
  • Check twice; the second check is the one that counts. The journal interface checks each call's arguments when the composer makes it, and raises an error at once, naming the composer. The journal interpreter checks again, because a journal is data given by the orchestrator, and can have been made by anything.

The guard can check what a command does from the command and the system: whether a file is one the constraints list, whether an account exists, whether a directory passes through a symbolic link. Of who asked, it knows for certain only the orchestrator account; see .

Gates

A process has a real uid, naming who started it, and an effective uid, the one the kernel checks for permission. Usually they are the same. When a person runs a program file marked setuid, the kernel sets the effective uid to that of the file's owner and leaves the real uid as the person's. A setuid program owned by root therefore runs with root's rights while still knowing who ran it. That is how passwd lets a person change his own password in /etc/shadow.

The gate is compiled because Linux ignores the setuid bit on a script started with #!: between the kernel opening the script and the interpreter reading it, the script could be swapped. The gate is the first few lines of its bespoke journal interpreter. It:

  1. finds the interpreter at a path fixed when the gate is compiled, relative to the gate itself, so an orchestrator cannot name another;
  2. refuses unless the interpreter, and every directory above it, is owned by root or by the interpreter account, and writable by no other account;
  3. clears the environment, setting only PATH and LANG, sets the file mode mask to 077, marks the process not dumpable, and changes directory to /;
  4. records the orchestrator account in MIG_ORCHESTRATOR_UID, MIG_ORCHESTRATOR_GID and MIG_ORCHESTRATOR_NAME;
  5. starts /usr/bin/python3 -E -s -B on the interpreter, passing the journal on standard input.

The Python part of the bespoke interpreter, before it imports anything, checks that every module it will load and its constraints file are owned by root or by the interpreter account, and writable by no other account. A module runs code when it is imported, so the check comes first.

These checks are made on every run, through a trivial gate as well as a blessed one, and whoever the orchestrator account is. A check that can be got around by other means still catches mistakes, such as a group-writable directory or an interpreter run from the wrong tree. Through a trivial gate the interpreter account is the person's own, so his own files pass.

Who is allowed to hand a journal to the interpreter is a constraint, not a rule of the gate's. The gate decides only whether the interpreter it would start can be trusted.

A trivial gate, one not blessed, changes no uid, so the interpreter account is the orchestrator account, and the guard still applies. The interpreter then accepts constraints given with --constraints, checked as its own files are, since nothing runs with more than the orchestrator account's own rights. When the gate changes the account, or the interpreter account is root, the interpreter refuses them and reads only its own constraints file. The trivial gate is the convenient way to use Man_In_Grey on files the person owns, and the way to prototype a command language before blessing a gate for it.

Least privilege, planned

Version 1.0 gates are setuid root, which gives the interpreter every one of root's rights. Root's rights are a set of about forty separate capabilities, among them CAP_DAC_OVERRIDE, to ignore file permissions; CAP_CHOWN, to change owners; CAP_SYS_ADMIN, to mount; and CAP_SETUID, to become another uid. The design is to give each gate only the capabilities its command language needs.

setcap stores chosen capabilities in a program file's extended attributes. A process running that file holds them while its uid stays the caller's. Capabilities are normally lost when a program execs one whose file holds none, as the gate does when it starts Python; the gate keeps them by raising them as ambient capabilities first, which survive the exec. A gate for the file language would then be able to write files and change owners, and nothing else. The gain is uneven: CAP_SYS_ADMIN, needed for mounting, is nearly root by itself.

Installation

A blessed gate and everything its interpreter loads are to be owned by root or by the interpreter account, in directories no other account can write, and the gate and the interpreter check this. A Harmony consumer/ directory is owned by the person who promoted into it, so a gate blessed there refuses to run, and so does root running the gate there. Installing a bespoke journal interpreter is a step of its own, done by root, or, when the interpreter account is not root, by root or by that account.

Command languages

A command language is defined once and used from both sides. Its composer half is its journal interface: one function per command, which checks the call's arguments, raises an error on a wrong one, and places the command. Its interpreter half is its checks, the constraint check among them, and the code that executes each command. Keeping both halves in one module keeps the two checks in step.

The command language is not specific to Man_In_Grey. An application that mounts home directories has a language of mount and unmount; one that manages accounts has a language for making and deleting them. A bespoke journal interpreter accepts one command language and refuses a journal written in another.

The file language

Man_In_Grey's own command language is a constrained form of the POSIX file interface:

Produces a symbol for the file. A relative directory is made absolute from the composer's working directory. permission is an integer such as 0o644, or three or four octal digits such as "0644". Appends content, text or bytes, to the file an open produced. Text is encoded as UTF-8. Removes a file. A file that is absent is not an error. The file must not exist. An existing file is discarded. An existing file is kept as <name>.YYYYMMDDTHHMMSSZ, the time in UTC, with .1, .2 added when that name is taken.

There is no close. Each opened file is written to a temporary file in its own directory, and after the journal's last command every opened file is given its owner and permission and put in place, each in one step: a rename for replace, a hard link that refuses an existing name for create, and for replace_keep a hard link of the old file to its backup name followed by the rename, so the file's name is never absent. Every directory is opened without following a symbolic link, and names are worked on inside the open directory.

Execution stops at the first error, and every temporary file not yet put in place is removed. An unlink earlier in the journal has already happened by then.

The interpreter checks a journal in four steps, each over every command, before executing any of it:

Known commands with exactly their arguments, of the right kinds; absolute directories in normal form; bare file names; every write naming the symbol of an open. The guard: the orchestrator account is listed; a requesting account is named only by an orchestrator account listed as a relay; every file opened or unlinked is listed, in that mode, with that owner and permission. Every owner names an account. Every directory exists, opens, and passes through no symbolic link; no file is named by two commands; a file opened in create mode does not exist; an existing file to be replaced or unlinked is a regular file.

The constraints of the file language are a JSON file:

{ "orchestrator_account": ["Thomas"], "relay_account": [], "file": [ {"directory": "/etc/unbound", "name": "unbound-US.conf", "mode": ["replace_keep"], "owner": "root", "permission": "0644"}, {"directory": "/etc/unbound", "name": "unbound-old.conf", "mode": ["unlink"], "owner": "root", "permission": "0644"} ] }

mode lists the open modes allowed for the file, and unlink when it can be removed. orchestrator_account lists the accounts allowed to give journals, and relay_account those of them allowed to name a requesting account. The constraints file installed with the interpreter lists no account and no file, so it refuses everything until root writes its own.

Accounts

Three programs take part in a run, and each runs as an account:

The orchestrator runs as it. The gate learns it from the kernel, as its real uid, and the orchestrator cannot misstate it. It is the one account the guard knows for certain. The composers run as it. Man_In_Grey runs composers in its own process, so its composer account is its orchestrator account. The guard and the general interpreter run as it. A trivial gate leaves it the orchestrator account; a blessed gate makes it the gate's owner.

The point of Man_In_Grey is that the work is done as the interpreter account while the composers run as another, with only the journal passing between them, and the guard deciding what of it is done. Code that runs as the composer account has no rights it did not already have. The common case has an unprivileged composer account and root as the interpreter account, but Man_In_Grey is not particular to privilege: any two accounts serve. A gate blessed to an ordinary account lets one person's composers change, within the constraints, files only that account can write.

The five arrangements

Each of the three accounts can be the same as another or different. The arrangements are the ways of grouping three things, of which there are five. (The 3! = 6 orderings of three things is a different count.)

The orchestrator runs the composers in its own process and invokes a trivial gate. The guard applies, and constraints can be given with --constraints. This is how a person uses Man_In_Grey on files he owns, how a command language is prototyped, and how the tester's test runs. When the one account is root, the composers have root's rights, and nothing stops one from changing files directly rather than through the journal; the guard checks only the journal. The orchestrator runs the composers in its own process and invokes a blessed gate. The case Man_In_Grey is made for. The AccountTree server works this way, with its own account composing and root interpreting. The orchestrator runs composers it does not trust as another account, and has the journal executed with its own rights through a trivial gate. The composers can do no harm while they run. The composers have the rights the journal is executed with, so they could make the changes themselves; the guard protects nothing against them. Of little use. The orchestrator runs composers as one account and has the journal executed as another, through a blessed gate.

Man_In_Grey as it stands gives arrangements 1 and 2, since its orchestrator runs composers in its own process. Arrangements 3 and 5 need an orchestrator that starts composers as another account, which takes root's rights or a gate of its own.

Whether an account is privileged is a separate matter from which accounts are the same. The guard needs only that the interpreter account can do what the orchestrator account asks of it, and the constraints say how much of that is allowed.

The requesting account

When a person runs Man_In_Grey for himself, he asked for the work, and he is the orchestrator account. In AccountTree, an account asks the server for work, such as a child account, and the server composes the journal and gives it to the interpreter. The server's account is then the orchestrator account, and the account that asked is the requesting account, named in the journal.

The guard cannot verify a requesting account named in the journal; it can verify only that the orchestrator account is entitled to name one. So a journal naming a requesting account is accepted only from an orchestrator account the constraints list in relay_account.

How the requests reach the orchestrator, and how it learns who made them, belongs to the application. The requests are not a Man_In_Grey command language: they go to the orchestrator, and only the journal it composes goes to the gate. The AccountTree server learns who asked from the kernel through SO_PEERCRED, so the chain from the requesting account to the guard rests on the kernel at both ends, and on the account listed in relay_account between them.

The journal

A journal is a CBOR map:

2. The name of the command language, such as file. Present when the work was asked for by an account other than the orchestrator account. When, where and by whom it was composed, and the composers that ran. The commands, each a map of command, argument, and composer. An argument that is a symbol is the map {"symbol": <index>}. Transports

A journal reaches its interpreter by starting the interpreter's gate with the journal on standard input. Since a journal is data, it could travel other ways, such as over a Unix domain socket to an interpreter already running, which would learn the orchestrator account through SO_PEERCRED. Man_In_Grey does not do this. It is the mechanism a program that receives requests is built with, not such a program itself.

Using Man_In_Grey Building

Man_In_Grey is a Harmony project with two namespaces: Man_In_Grey.copy, the Python programs, and Man_In_Grey_file_gate.make, the gate of the file language's interpreter. In the developer role, build "*" and promote write place them in the layout every part finds its partners by:

consumer/Man_In_Grey/Man_In_Grey the command a person runs consumer/Man_In_Grey/Man_In_Grey.py compose and orchestrate: run composers, make the journal consumer/Man_In_Grey/Journal.py symbols, commands, the journal, CBOR consumer/Man_In_Grey/FileLanguage.py the file language, both halves consumer/Man_In_Grey/journal_interpreter.py the general interpreter consumer/Man_In_Grey/journal_interpreter_file.py the file language's bespoke interpreter consumer/Man_In_Grey/constraints_file.json its constraints, refusing everything consumer/Man_In_Grey_file_gate/Man_In_Grey_file_gate the gate

The same layout is staged in developer/scratchpad/made/, so a developer's experiment runs from there. Both sides need the Python package cbor2, each in its own Python. Man_In_Grey, and any program using the journal interface, runs on the first python3 on PATH, which in a Harmony role is the project's linked Python when there is one; install the package into it with python3 -m pip install cbor2. The gate always starts /usr/bin/python3 -E -s, so the interpreter uses neither a person's Python nor a copy installed with pip install --user into ~/.local. The system Python needs the package from the distribution, installed by root. openSUSE names the package for the Python it is built for, so for Python 3.13 it is python313-cbor2. To see what the interpreter will see: /usr/bin/python3 -E -s -c 'import cbor2; print(cbor2.__file__)'.

Writing composers

Composers are kept in a directory named, by Harmony's convention, composer, since every file in it is one. Each is a Python file defining compose(prov ,journal_iface). Its place in the directory carries no meaning; where its files go is said by its open and unlink commands.

# composer/unbound-US.conf.py def compose(prov ,journal_iface): file = journal_iface.open("/etc/unbound" ,prov.implied_fname ,"replace_keep" ,"root" ,0o644) journal_iface.write(file ,"server:\n verbosity: 1\n") The composer's own file name less .py, for a composer named for the file it writes. The name of the person who ran Man_In_Grey. The composer directory, the composer's path absolute and relative to it, the directory holding the composer, and the working directory of the run.

Man_In_Grey compose <file> runs one composer. Man_In_Grey orchestrate <directory> runs every .py file in the directory whose name does not begin with a dot, breadth first and then by name; --input_acceptance names a Python file defining accept(prov) to choose otherwise. Nothing chosen when Man_In_Grey is run reaches compose; settings are written into the composer.

Running

A run that changes files is best preceded by two that do not. The first shows the journal while nothing has left the person's account; the second has the interpreter check the journal and stop before executing it:

Man_In_Grey orchestrate composer --phase-1-print --phase-1-then-stop Man_In_Grey orchestrate composer --phase-2-filesystem-then-stop Man_In_Grey orchestrate composer Run the one composer in the file. Run every composer in the directory. The acceptance filter. The gate to hand the journal to. Default: ../Man_In_Grey_file_gate/Man_In_Grey_file_gate from Man_In_Grey.py. Constraints for a run through a trivial gate; refused when the gate changes the account or the interpreter account is root. Stop after checking the path and the filter. Print the journal after composing; stop after composing. Print the journal as the interpreter decoded it; stop after decoding. Stop after the named check, reporting OK when it passed.

The command and its path come first, and the options follow; given no arguments, Man_In_Grey prints its help. The exit status is 0 when the run did what it was asked, 1 when a check refused the journal or a command failed, and 2 when the run could not start or a composer failed, a wrong argument to the journal interface included. To undo a replace_keep, rename the backup back.

Installing a blessed interpreter

As root, copy consumer/Man_In_Grey/ and consumer/Man_In_Grey_file_gate/ side by side into a directory owned by root and writable by no other account, make every file owned by root and not group- or other-writable, write the constraints into constraints_file.json, and bless the gate to the interpreter account. For root:

chown root:root Man_In_Grey_file_gate/Man_In_Grey_file_gate chmod 4755 Man_In_Grey_file_gate/Man_In_Grey_file_gate Man_In_Grey_file_gate/Man_In_Grey_file_gate --print-flags

4755 is the mode 755 with the setuid bit, 4000, added. For an interpreter account other than root, the gate is owned by that account and its group, and given the setgid bit, 2000, as well, as chmod 6755. Only root can give a file away, so an interpreter running as another account can make files only that account owns, and its group has to be that account's group too. --print-flags reports the real and effective uid, and whether the gate changes the account. Promotion replaces files and does not bless, so the installation is redone after each promotion that changes the interpreter. The installation step is a candidate for Man_In_Grey itself, once there is a language for installing programs.

Testing

The tester's test tester/authored/write_file runs the promoted Man_In_Grey through an unblessed gate, with constraints it writes into its scratchpad directory, and checks nineteen things. Two runs of composers using every mode and unlink are compared with expected/run_1 and expected/run_2, with backup times replaced by the letters YYYYMMDDTHHMMSSZ. A file opened in create mode is written once and refused the second time. A journal with one allowed file and one the constraints do not list is refused whole. A composer giving a wrong mode fails before any journal reaches the gate. Each refusal leaves every file as it was. Since the gate checks ownership on every run, every directory from / down to the promoted interpreter is to be writable by no account but its owner. In the tester role:

authored/write_file/run test authored/write_file/run clean Known problems The old compile script built the gate with -z relro, -z now and -fstack-protector-strong. Harmony's build has no flags for one namespace, so the gate is built without them. Execution stops at the first error and removes the temporary files of files not yet put in place, but an unlink that ran earlier in the journal stays done. The filesystem check and execution are separate, so a file can appear or change between them. Execution then fails on that command rather than acting on the change: a create whose file has appeared is refused by the hard link. The journal and the guard carry a requesting account, but Man_In_Grey has no option to name one, and no test uses one. A program using the journal interface as a library sets it when it makes the journal. When the interpreter fails to start, for example because the system Python lacks cbor2, Python exits with status 1, the status of a refused journal.  Changes from the first version

The first version had configuration programs calling a planner, a plan, a fixed set of operations, copy, displace and delete, an inner executor, and one gate, man_in_grey_apply, that accepted --inner <file> from its caller. That option let any account in the group sudo run a program of its choosing with root's rights, without a password. The present design fixes the interpreter's path in its gate, moves the decision about orchestrator accounts into the constraints, raises an error in the composer on a wrong argument where the first version dropped the command silently, replaces a scope fence that the gate's change of directory made ineffective with constraints naming each file, removes temporary files after a failure, and gives a second backup within one second a name of its own.
