Purpose

The Man_In_Grey tools were created to facilitate the controlled generation and installation of system configuration files, such as the files under /etc. These tools can be used, for example, to complete unprivileged account builds that require system configuration file changes, and to support programs that run from unprivileged accounts but, as a normal part of their operation, require configuration file changes.

With the Man_In_Grey approach, an application running with the real and effective uid of account A composes a journal, and that journal is given to a program called the gate. The gate is owned by account B and setuid, so that when invoked it runs with the effective uid of account B. Internally the gate first invokes a program called the guard to approve the journal. If approved the gate invokes another program called the interpreter, which plays the journal.

An application making use of Man_In_Grey can provide its own composer, guard, and interpreter. Consequently, each application that makes use of Man_In_Grey can have a different instruction language for the journal. Man_In_Grey merely provides the scaffolding.

This document is both the design of Man_In_Grey and the user manual, as Man_In_Grey is a programmer's tool.

It is given a composer file or a composer directory, runs the composers, all of them placing instructions into one journal, and invokes a gate with that journal on its standard input. A grammar that describes the available instruction formats. Each instruction currently has the format of an instruction operation specifier followed by arguments. Out-of-band signaling

Man_In_Grey provides an alternative to templates. In template systems an output file, such as a configuration file, is generated by a blank filling program. With Man_In_Grey the output file is written by interpreting a journal, and the journal is written by a composer.

There are problems with the method of filling in templates, for one it mixes data and control together: the content to be written, and the marks that say where to substitute. Thus templating is a form of in-band signaling. With in-band signaling, a content string can be identical to a control string, so data and control can alias, and there is no tight way to design the aliasing out. The typical workaround is to disallow control strings in the data, and to write each disallowed character as an escape sequence, where the escape is then itself control. Each level of nesting multiplies the escapes: an f-string that explains how to write f-strings escapes its braces has twice the number of escapes as the base f-string, and a document about this f-string escapes them again, to have 4 times the number, etc.

Man_In_Grey signals out of band. A composer is a program, so the logic that forms the output is code, with loops, conditions and lookups, rather than marks embedded in the output. An instruction in the journal is a structure, and file content is carried in it as a byte string with its length. The journal interpreter never scans content for meaning, so content can hold anything, including text that looks like a journal, with no escaping. (A developer is free to create a composer that fills in templates if that is what he really wants; but there is no inherent need to use this approach.)

The journal is encoded in CBOR, whose strings are length-prefixed. Decoding CBOR makes maps, lists, strings and bytes, and cannot run code, so a journal reaches account B as data and nothing else.

Man_In_Grey replaces the template, not the syntax of the file being written. Content is still to be well formed for the program that reads the file, so a composer writing HTML escapes a < in its text as HTML requires. An instruction language can take that work over too, as the example in does.

Symbol

A composer writes instructions, but it does not run them. When an instruction would produce a result when run, as for example the file open instruction, which returns a file handle, the result does not exist yet at the time the composer runs. Hence, when an instruction is entered into the journal via the journal interface, the interface returns a symbol placeholder. The symbol is then used as an argument by the composer when it enters instructions that are given said result as an argument. In the current implementation a symbol is simply the index into the journal that locates an instruction. Thus, with the current implementation each instruction can have at most one result.

file = journal_iface.open("/etc/unbound" ,"unbound-US.conf" ,"replace_keep" ,"root" ,0o644) journal_iface.write(file ,"server:\n verbosity: 1\n")

In this example file is a result symbol. The value of file will be 0, i.e. the index into the journal of the open instruction.

Permissions uid

Each account has a number called its user id, or uid. Each file has an owner, noted with a uid. Each process is associated with two uids, its real uid and its effective uid. When a person logs in, the login program starts his shell with both uids set to that of his account, and every process started from the shell inherits them. In colloquial speech such processes are said to be owned by the person, or to run under his account. However, the two uids associated with a process can differ, so these colloquialisms are imprecise.

The effective uid determines a process's permissions. So for example when opening a file, the kernel compares the process's effective uid with a file's owner and permission bits to determine if the process is allowed to open the file. Among its other uses, the kernel lets a process send a signal to another process whose real uid equals its own real or effective uid.

A process inherits both uids from the process that invoked it, unless the program file it runs has its setuid permission bit set. In which case, the kernel then takes the effective uid from the file's owner instead, while the real uid remains inherited as before. A process therefore gets its effective uid in one of two ways: from the process that invoked it, or from the owner of a setuid program file. (Groups work the same way, with a real gid, an effective gid and a setgid bit, beside the supplementary groups, which are inherited unchanged.)

By convention, the gate is the only program of Man_In_Grey that can optionally be given the setuid bit. When the gate is not setuid, it inherits its effective and real uids from the program that invoked it. When it is setuid, it inherits its real uid from the program that invoked it, and it inherits its effective uid from its file owner. Thus, the gate process has reliable information directly from the kernel on who invoked it, as that is its real uid. It also has reliable information directly from the kernel on who owned its executable file, as that becomes its effective uid.

Due to this mechanism the effective uid for a setuid gate program can be different than the effective uid of the program that invoked it. In the chain of events of program A running and then invoking the gate, the effective uid in that thread of execution will start as the effective uid for program A, and then the effective uid will change to match the uid of the gate executable file owner. We can say that the effective uid change from A to B, where A is the invoking programs effective uid, an B is the owner of the gate executable file.

Orchestrator

The orchestrator is a utility program provided with Man_In_Grey. The orchestrator calls one or more composer programs, then sends the resulting journal to a gate program. Like all processes, when the orchestrator program runs, it has a real and effective uid. When the orchestrator is run from a shell, these are both inherited from the shell, and are typically pointing to the login user. In any case, the composers that it invokes will then run with the same effective and real uids as the orchestrator. When the gate executable file has its setuid bit set, when the gate is invoke by the orchestrator, the gate will inherit its real uid from the orchestrator, and will take its effective uid from the gate's executable file owner.

An application making use of Man_In_Grey can bypass the orchestrator and call the composers and gate on its own. When this happens the gate's real ID will be that of the application. For a setuid gate, its effective uid still comes from its file owner.

It is possible that the application is design such that the gate executable file does not have its setuid bit set, or that it does have its setuid set but the gate owner is the same as that of the orchestrator or that of the direct calling application. In such a case, the execution thread will keep the same real and effective uids the entire time it runs. In this mode the Man_In_Grey can not achieve anything the application could not have achieved on its own, but it still might be a convenient expression of the desired functionality.

Gate

The gate is compiled because Linux ignores the setuid bit on a script started with #!. Given no arguments, the gate prints its usage. Its command flags reports the gate's real and effective uid and gid with their names, whether they differ, the name of the gate's instruction language, and the paths of the guard and the interpreter.

2026-11-06 07:55:01 Z [:] Thomas·developer@IdealX §/home/Thomas·developer/project/Man_In_Grey/consumer§ > ./Man_In_Grey_gate/Man_In_Grey_file_gate flags real.uid=2005 real.user_name=Thomas·developer real.gid=2005 real.group_name=Thomas·developer effective.uid=2005 effective.user_name=Thomas·developer effective.gid=2005 effective.group_name=Thomas·developer uid_differ=0 gid_differ=0 language=file guard.path=/home/Thomas·developer/project/Man_In_Grey/consumer/Man_In_Grey/guard_file.py interpreter.path=/home/Thomas·developer/project/Man_In_Grey/consumer/Man_In_Grey/interpreter_file.py

Th admit command takes the journal on standard input, with the options constraints <file> and check_only. When the gate is asked to admit a journal, it:

  1. opens /dev/null on any of descriptors 0, 1 and 2 the invoking program left closed, and closes every descriptor above 2, so nothing the invoking program opened reaches the guard or the interpreter;
  2. raises each resource limit that could stop the guard or the interpreter partway, file size and CPU time to unlimited, address space and data size to 1 GiB, stack size to 8 MiB, and open files to 64, as far as the hard limit allows, or past it when account B is root; and refuses when one stays too low;
  3. finds the guard and the interpreter at paths fixed when the gate is compiled, relative to the gate itself, so account A cannot name others;
  4. refuses unless the guard and the interpreter, and every directory above them, are owned by root or by account B, and writable by no other account;
  5. clears the environment, setting only PATH and LANG, sets the file mode mask to 077, marks the process not dumpable, and changes directory to /;
  6. records its real ids, account A's, in MIG_REAL_UID, MIG_REAL_GID and MIG_REAL_USER_NAME;
  7. reads the journal from its standard input, up to 16 MiB;
  8. starts /usr/bin/python3 -E -s -B on the guard, with the journal on its standard input, and goes on only when the guard approves the journal;
  9. starts the interpreter the same way, with the same journal.

The guard and the interpreter, before they import anything, each check that every module they load, and the guard its constraints file, are owned by root or by account B, and writable by no other account. A module runs code when it is imported, so the check comes first.

These checks are made on every run, whether or not the gate is setuid, and whoever account A is. A check that can be got around by other means still catches mistakes, such as a group-writable directory or an interpreter run from the wrong tree. When accounts A and B are the same, account B is the person's own account, so his own files pass.

The constraints, not the gate, decide which accounts can give a journal. The gate decides only whether the guard and the interpreter it would start can be trusted, and whether the guard approved the journal.

A gate that is not setuid keeps the uids of the program that invoked it, so accounts A and B are normally the same, and the guard still applies. When they are the same, the guard and the interpreter accept constraints given with constraints <file>, which the gate passes to both, checked as their own files are, since nothing runs with more than account A's own rights. When they differ, or account B is root, both refuse them and read only the constraints file installed beside them. A gate that is not setuid is the convenient way to use Man_In_Grey on files the person owns, and the way to prototype an instruction language before making a gate setuid for it.

One gate per instruction language

Man_In_Grey's general gate is the library module Gate.lib.c, whose function Man_In_Grey_gate·Gate·run takes the name of the instruction language, the guard's path and the interpreter's path, and the command line. An instruction language's gate is a *.CLI.c of three lines that calls it with the three fixed. The gate of the file language:

#include "Gate.lib.c" int main(int argc ,char **argv){ return Man_In_Grey_gate·Gate·run("file" ,"../Man_In_Grey/guard_file.py" ,"../Man_In_Grey/interpreter_file.py" ,argc ,argv); }

The general gate is curried, with its first three arguments supplied when the gate is compiled. Whoever invokes a gate can choose neither program it runs; if he could, he could give it a guard that approves everything. The language name holds no space and no control character, and the gate refuses to run when it does. Man_In_Grey has two gates: the file language's, above, and Man_In_Grey_emplace_bio_gate, the gate of the example language in .

Output rule

Every line the guard and the interpreter write is copied to the person, marked guard: or interpreter:, and to the system log under the name Man_In_Grey_gate, beside the gate's own lines, marked gate:, saying who asked and what the gate decided. A line breaks the gate's rules when it is not UTF-8, or holds a control character (C0, DEL or C1), or is longer than 4096 bytes, or is one line more than 2000; the gate then stops the program and refuses the journal. Unicode is otherwise welcome, file names in Chinese included. The guard writes any control character it quotes as \u{XXXX}, and the wellformed check refuses a directory, file name or owner that holds one.

Least privilege, planned

A setuid gate owned by root gives the interpreter every one of root's rights. Root's rights are a set of about forty separate capabilities, among them CAP_DAC_OVERRIDE, to ignore file permissions; CAP_CHOWN, to change owners; CAP_SYS_ADMIN, to mount; and CAP_SETUID, to become another uid. The design is to give each such gate only the capabilities its instruction language needs.

setcap stores chosen capabilities in a program file's extended attributes. A process running that file holds them while its real and effective uid stay account A's. Capabilities are normally lost when a program execs one whose file holds none, as the gate does when it starts Python; the gate keeps them by raising them as ambient capabilities first, which survive the exec. A gate for the file language would then be able to write files and change owners, and nothing else. The gain is uneven: CAP_SYS_ADMIN, needed for mounting, is nearly root by itself.

Installation

A setuid gate and everything its guard and interpreter load are to be owned by root or by account B, in directories no other account can write, and the gate and the interpreter check this. A Harmony consumer/ directory is owned by the person who promoted into it, so a setuid gate there refuses to run, and so does root running the gate there. Installing an instruction language's gate, guard and interpreter is a step of its own, done by root, or, when account B is not root, by root or by account B. The steps are in .

Guard

Accounts exist to limit what programs can do. The guard decides, before anything runs with the effective uid of account B, whether the work account A asks for is allowed: it reviews the journal and checks it against a set of constraints, and approves the journal only when every constraint is met.

The kernel tells the gate which account invoked it, as the real uid, and the gate passes it on, so the guard knows it also. The kernel does not say which program invoked the gate. As the guard invocation is compiled into the gate, the guard can know the provenance of the journal from the point it was given to the gate, but not before that.

Two checks are needed by nearly every guard, whatever its instruction language. The first is that the journal is well formed: that it decodes, names only instructions of its language, and gives each instruction the arguments it takes, of the right kinds. This check carries knowledge of the instruction syntax, so it belongs to the instruction language, and the interpreter makes it again before executing. The second is who account A is. The gate's real uid is account A's, and its real gid and supplementary groups are those it inherited from the invoking program, since the setuid and setgid bits change only the effective ids. All three pass to the guard, which reads them from the kernel, so account A cannot misstate them. A guard can therefore allow a journal from accounts its constraints list, or from the members of a group they name. The file language's guard checks account A by name; a check by group is not yet made.

The other checks a guard makes belong to its instruction language. The file language's four checks are in .

Verdict

A guard reads the journal on its standard input. Its standard error is for the person: one line per finding, as <tag>: <message>, the first two name: and version:, then such lines as check_passed: wellformed or constraint_broken: <what is wrong>. Its standard output is for the verdict alone. A guard approves a journal by writing exactly one line there, guard <language> check passed, with the language name the gate has compiled in, and exiting 0. The gate takes the journal as approved on that line and that status together, and on nothing else, and only then admits it to the interpreter; a guard that refuses exits 1, and one that cannot check exits 2.

The verdict travels out of band from the findings. A finding quotes the journal, a file name for instance, and goes to standard error, so nothing in a journal can put a line on standard output. A crash cannot approve a journal either: an uncaught Python exception exits 1, and a guard that dies leaves no verdict.

Interpreter

The gate starts the interpreter only after the guard has approved the journal, with the effective uid of account B and the same journal on its standard input. The interpreter does not check the constraints; that is the guard's work. It reads them, from the same file as the guard, only for what execution needs, as the example language's interpreter takes from them the directory its pages go in. It decodes the journal, checks once more that the journal is well formed, and then executes the instructions in order.

The interpreter writes one line to standard output for each thing it does, as <tag>: <message>, and the gate copies each line to the person and to the system log by the output rule. Its exit status is 0 when the journal was executed, 1 when execution failed, and 2 when the journal could not be read or is not well formed.

Execution stops at the first error. What the interpreter did before then stays done, except what its instruction language undoes; for the file language, see .

Instruction language

An instruction language is defined once and used from both sides. Its composer half is its journal interface: one function per instruction, which checks the call's arguments, raises an error on a wrong one, and places the instruction. Its other half is the checks the guard makes, the constraint check among them, and the code the interpreter runs for each instruction. Keeping both halves in one module keeps the two checks in step.

The instruction language is not specific to Man_In_Grey. An application that mounts home directories has a language of mount and unmount; one that manages accounts has a language for making and deleting them. Each gate starts the guard and the interpreter of one instruction language, and they refuse a journal written in another.

A language can be made as narrow as its application. The narrower it is, the less a journal can say, and the less the guard has to rule out. The file language can name any file, so its constraints list the files allowed. The example language, , can name no file at all: what it writes, and where, follows from the account that gives the journal.

The file language

Man_In_Grey's own instruction language is a constrained form of the POSIX file interface:

Produces a symbol for the file. A relative directory is made absolute from the composer's working directory. permission is an integer such as 0o644, or three or four octal digits such as "0644". Appends content, text or bytes, to the file an open produced. Text is encoded as UTF-8. Removes a file. A file that is absent is not an error. The file must not exist. An existing file is discarded. An existing file is kept as <name>.YYYYMMDDTHHMMSSZ, the time in UTC, with .1, .2 added when that name is taken.

There is no close. Each opened file is written to a temporary file in its own directory, and after the journal's last instruction every opened file is given its owner and permission and put in place, each in one step: a rename for replace, a hard link that refuses an existing name for create, and for replace_keep a hard link of the old file to its backup name followed by the rename, so the file's name is never absent. Every directory is opened without following a symbolic link, and names are worked on inside the open directory.

Execution stops at the first error, and every temporary file not yet put in place is removed. An unlink earlier in the journal has already happened by then. The interpreter writes a line for each thing it does, such as replaced: /etc/unbound/unbound-US.conf (kept as unbound-US.conf.20261105T083807Z).

The guard checks a journal in four steps, each over every instruction, and stops at the first step that finds a problem. It reports each problem as <step>_broken and each step that passes as check_passed:

Known instructions with exactly their arguments, of the right kinds; absolute directories in normal form; bare file names; no control character in a directory, file name or owner; every write naming the symbol of an open. Account A is listed in gate_invoking_account; every file opened or unlinked is listed, in that mode, with that owner and permission. Every owner names an account. Every directory exists, opens, and passes through no symbolic link; no file is named by two instructions; a file opened in create mode does not exist; an existing file to be replaced or unlinked is a regular file.

The constraints of the file language are a JSON file:

{ "gate_invoking_account": ["Thomas"], "file": [ {"directory": "/etc/unbound", "name": "unbound-US.conf", "mode": ["replace_keep"], "owner": "root", "permission": "0644"}, {"directory": "/etc/unbound", "name": "unbound-old.conf", "mode": ["unlink"], "owner": "root", "permission": "0644"} ] }

mode lists the open modes allowed for the file, and unlink when it can be removed. gate_invoking_account lists the accounts allowed to be account A, giving journals to the gate. The constraints file installed with the interpreter lists no account and no file, so it refuses everything until it is replaced by the constraints the application developer wrote.

Journal

A journal is a CBOR map:

3. The name of the instruction language, such as file. When, where and by whom it was composed, and the composers that ran. The instructions, each a map of name, argument, and composer. An argument that is a symbol is the map {"symbol": <index>}. Transport

A journal reaches its interpreter by starting the interpreter's gate with the journal on standard input. Since a journal is data, it could travel other ways, such as over a Unix domain socket to an interpreter already running, which would learn account A through SO_PEERCRED. Man_In_Grey does not do this. It is the mechanism a program that receives requests is built with, not such a program itself.

Using Man_In_Grey Building

Man_In_Grey is a Harmony project with two namespaces: Man_In_Grey.copy, the Python programs, and Man_In_Grey_gate.make, the general gate and the gates of the file language and the example language. In the developer role, from its directory developer/, build "*" and promote write place them in the following layout, which is how each part finds the others:

consumer/Man_In_Grey/Man_In_Grey the command a person runs consumer/Man_In_Grey/Man_In_Grey.py the orchestrator consumer/Man_In_Grey/install_gate installs a gate setuid, run by root consumer/Man_In_Grey/Journal.py symbols, instructions, the journal, CBOR consumer/Man_In_Grey/Constraint.py loading the constraints consumer/Man_In_Grey/Guard.py the general guard consumer/Man_In_Grey/Interpreter.py the general interpreter consumer/Man_In_Grey/FileLanguage.py the file language: interface, checks, execution consumer/Man_In_Grey/guard_file.py the file language's guard consumer/Man_In_Grey/interpreter_file.py the file language's interpreter consumer/Man_In_Grey/constraints_file.json its constraints, refusing everything consumer/Man_In_Grey/EmplaceBioLanguage.py the example language consumer/Man_In_Grey/guard_emplace_bio.py its guard consumer/Man_In_Grey/interpreter_emplace_bio.py its interpreter consumer/Man_In_Grey/constraints_emplace_bio.json its constraints, refusing everything consumer/Man_In_Grey_gate/Man_In_Grey_file_gate the file language's gate consumer/Man_In_Grey_gate/Man_In_Grey_emplace_bio_gate the example language's gate consumer/Man_In_Grey_gate/libMan_In_Grey.a the general gate, for other gates

The same layout is staged in developer/scratchpad/made/, so an experiment in the developer role of the Man_In_Grey project runs from there. Both sides need the Python package cbor2, each in its own Python. Man_In_Grey, and any program using the journal interface, runs on the first python3 on PATH, which in a Harmony role is the project's linked Python when there is one; install the package into it with python3 -m pip install cbor2. The gate always starts /usr/bin/python3 -E -s, so the guard and the interpreter use neither a person's Python nor a copy installed with pip install --user into ~/.local. The system Python needs the package from the distribution, installed by root: python-cbor2 on Arch, python3-cbor2 on Debian, and on openSUSE, which names packages for the Python they are built for, python313-cbor2 for Python 3.13. To see what the interpreter will see: /usr/bin/python3 -E -s -c 'import cbor2; print(cbor2.__file__)'.

Writing a composer

Composers are kept in a composer directory, named composer in the examples here. Every file in it is a composer, a Python file defining compose(prov ,journal_iface); notes such as a README belong a directory up. Its subdirectories are namespaces for the author. They set the order the composers run in: depth first, in order of name at each level, files and subdirectories together, by Unicode code point, so capital letters come before small ones. A composer's place says nothing else; its open and unlink instructions say where its files go.

A composer runs with the orchestrator's uids, which are normally account A's, and so with account A's rights. If another account could change a composer, or add one to a composer directory, that account's code would run with account A's rights, and its instructions would reach the gate in account A's name. Every composer, and every directory from / down to it, is therefore to be owned by account A or by root, and writable by no other account.

This ownership protects account A, not account B, and the gate cannot enforce it. The gate is given a journal, never the program that made it, and anything it is told about the composers comes from account A. To the gate and the guard, every journal is account A's, whatever made it. Composer ownership is therefore a convention, kept by whoever installs an application's composers. Man_In_Grey's orchestrator keeps it for its own runs: before running any composer it makes the check, and it refuses a symbolic link in a composer directory. An application that acts as its own orchestrator keeps the convention itself. To run a composer someone else wrote, review it and copy it into your own composer directory.

# composer/unbound-US.conf.py def compose(prov ,journal_iface): file = journal_iface.open("/etc/unbound" ,prov.implied_fname ,"replace_keep" ,"root" ,0o644) journal_iface.write(file ,"server:\n verbosity: 1\n") The composer's own file name less .py, for a composer named for the file it writes. The name of account A. The composer directory, the composer's path absolute and relative to it, the directory holding the composer, and the working directory of the run.

Man_In_Grey orchestrate <path> runs the one composer in a composer file, or every composer in a composer directory. No option given to Man_In_Grey reaches compose; a composer's settings are written in the composer itself. The journal_iface a composer is given is that of the gate's instruction language: the orchestrator asks the gate for its flags, and loads the module named for its language, FileLanguage.py for file and EmplaceBioLanguage.py for emplace_bio.

Running

A run that changes files is best preceded by two that do not. The first shows the journal while nothing has left the person's account; the second has the guard check the journal, and the gate stop before the interpreter:

Man_In_Grey orchestrate composer print compose_only Man_In_Grey orchestrate composer check_only Man_In_Grey orchestrate composer Run the composer in a composer file, or every composer in a composer directory, and invoke the gate with the journal. The gate to invoke, which also sets the instruction language the composers write in. Default: ../Man_In_Grey_gate/Man_In_Grey_file_gate from Man_In_Grey.py. Constraints for a run in which accounts A and B are the same, given to the guard and the interpreter; refused when they differ or account B is root. Print the journal after composing. Stop after composing; nothing reaches the gate. Have the gate run the guard and not the interpreter.

The command and its path come first, and the options follow, as plain words; given no arguments, Man_In_Grey prints its help, and so does the gate. The exit status is 0 when the run did what it was asked; 1 when the guard refused the journal or an instruction failed to execute; and 2 when the run could not start, a composer failed or was refused, or the gate, guard or interpreter could not run or broke the gate's rules. The guard's and interpreter's lines are also in the system log; on a system with journald, journalctl -t Man_In_Grey_gate shows them. To undo a replace_keep, rename the backup back.

Installing a setuid gate

A setuid gate is installed by root, with install_gate, which is promoted beside Man_In_Grey:

sudo consumer/Man_In_Grey/install_gate install <gate> owner <account> into <directory> [constraints <file>]

It copies Man_In_Grey/ and the one gate named from Man_In_Grey_gate/ into the directory, side by side, as the gate's compiled paths expect. Every file and directory it installs is owned by root and writable by no other account, except the gate, which it gives to account B, the owner account named, and then makes setuid. The order matters, since changing a file's owner clears its setuid bit. For root as account B the gate's mode is 4755, the mode 755 with the setuid bit, 4000, added. For any other account B it is 6755, with the setgid bit, 2000, too, and account B's group as the gate's group. Only root can give a file away, so an interpreter whose effective uid is that of an account B other than root makes files account B owns, with the effective gid's group; setgid makes that account B's group.

The constraints given with constraints <file> are installed as constraints_<language>.json. Without the option, an installed constraints file is kept, and a first installation gets the one promoted with Man_In_Grey, which refuses everything. install_gate refuses a directory that is not absolute, that an account other than root owns or can write, or that is on a file system mounted nosuid, where the kernel ignores the setuid and setgid bits, as it does on removable drives and some separately mounted /home directories. It ends by printing the installed gate's flags, as root sees them: real uid root's, effective uid account B's. Promotion replaces files and sets neither the owner nor the setuid bit, so the installation is redone after each promotion that changes the gate, the guard or the interpreter. The installation is a candidate for Man_In_Grey itself, once there is a language for installing programs.

Testing

The tester has two tests. Each runs the promoted Man_In_Grey through a gate that is not setuid, so accounts A and B are the same, with constraints it writes into its scratchpad directory. The test tester/authored/write_file runs the file language's gate, and checks twenty-five things. Two runs of composers using every mode and unlink are compared with expected/run_1 and expected/run_2, with backup times replaced by the letters YYYYMMDDTHHMMSSZ. A file opened in create mode is written once and refused the second time. A journal with one allowed file and one the constraints do not list is refused whole. A composer giving a wrong mode fails before any journal reaches the gate. A composer directory holding a composer other accounts can write is refused by the orchestrator. A check_only run is approved by the guard and changes nothing. A run under a file size limit the gate cannot raise is refused before the guard starts. Each refusal leaves every file as it was. Since the gate checks ownership on every run, every directory from / down to the promoted interpreter is to be writable by no account but its owner. In the tester role, from its directory tester/:

authored/write_file/run test authored/write_file/run clean

The test tester/authored/emplace_bio runs the example language's gate, and checks twenty-six things. A page with every style and with text that looks like markup is compared with expected/page.html, and its picture with the one given. A later run with a JPEG places it and removes the PNG, and a run with no picture removes the JPEG. A check_only run changes nothing. Seven journals are then made without the journal interface and given to the gate directly, as a program other than the orchestrator could: one whose text instruction carries a file name, one with a style the language does not have, one with text before any paragraph, one with an SVG picture, one with more text than its constraints allow, one from an account its constraints do not list, and one for a page that has been made a symbolic link. Each is refused by the check that is to refuse it, and changes nothing:

authored/emplace_bio/run test authored/emplace_bio/run clean Example: emplace_bio

A host publishes a bio page for each of the accounts it allows, at /srv/http/bio/<user_name>.html, with the account's picture beside it. The directory belongs to the web server's account, http on Arch and www-data on Debian, so a person cannot write his page there himself. He writes a composer giving his display name, his text and his picture, and runs Man_In_Grey with the gate Man_In_Grey_emplace_bio_gate, which the administrator has installed setuid to the web server's account. The interpreter then runs with the effective uid of http, and builds the page.

Here account B is not root, and the gate stands between two ordinary accounts. The example is made so that a reader can see each step is safe: a person can change only his own page, and only to a page made of his text and picture.

The instruction language The page's title and heading. Given once. Starts a paragraph. A run of text in the current paragraph. style is a list drawn from strong, emphasis, underline and strikethrough; an empty list is plain text. The bytes of a PNG or JPEG image. At most once.

No instruction names a file. The page's file names come from the user name of the real uid, which the kernel gives the guard and the interpreter, so a person can write only his own page. The directory comes from the constraints, which the administrator installs. A journal describes the whole page: a run that gives no picture removes the picture an earlier run placed.

Decoration travels out of band. A run's styles are a list beside its text, not marks in it, and the interpreter turns each style into one fixed tag with no attribute: <strong>, <em>, <u> and <s>, nested in that order. It writes the rest of the page from a fixed form, and escapes every text it is given, so nothing a person gives becomes markup. There is nothing to sanitize: an attribute such as onload, or a <script> element, cannot be expressed in the language.

The composer

The composer is Thomas's own program, running with his uid. It holds the text in code and reads the picture from beside the composer directory:

# composer/bio.py from pathlib import Path DISPLAY_NAME = "Thomas" BIO = [ [("I write " ,[]) ,("software" ,["emphasis"]) ,(" and " ,[]) ,("documentation" ,["strong"]) ,("." ,[])] ,[("Text such as <b>this</b> is shown as written." ,[])] ] def compose(prov ,journal_iface): journal_iface.display_name(DISPLAY_NAME) for paragraph in BIO: journal_iface.paragraph() for content ,style in paragraph: journal_iface.text(content ,style) journal_iface.picture((Path(prov.composer_root_dpath).parent / "picture.jpg").read_bytes())

A composer could as well read a file in a notation its author likes, such as *emphasis*, and turn it into runs. That conversion runs with the person's own uid, so a mistake in it stays on his side; the gate only ever receives runs and style names.

The constraints { "gate_invoking_account": ["Thomas", "Alice"], "directory": "/srv/http/bio", "text_max_bytes": 8192, "picture_max_bytes": 1048576 }

One constraints file serves every account, since the page's name follows from the account. gate_invoking_account lists the accounts that can have a page. text_max_bytes bounds the display name and text together, and picture_max_bytes the picture.

The guard Only the four instructions, with exactly their arguments; one display name; at most one picture; text only within a paragraph, and no paragraph without text; every style one of the four, none twice; no control character in any text. Account A is listed in gate_invoking_account; the text and the picture are within their limits; the constraints give an absolute directory. The picture begins with the signature of a PNG or a JPEG file. SVG is refused on purpose: it is a document that can hold script, and run it when opened by itself. The directory exists, is reached through no symbolic link, and can be written by the effective uid's account; the account's page and pictures, where they exist, are regular files.

The filesystem check asks whether the effective uid can write the directory. Python's os.access, like the system call access under it, answers for the real uid unless asked with effective_ids=True, since it was made for setuid programs to ask what the person who ran them could do.

The interpreter

The interpreter writes the picture and the page to temporary files in the directory, gives each permission 0644, and renames each into place, then removes a picture the page no longer shows. The files are owned by http, the effective uid that made them. The page Thomas's composer gives:

<!DOCTYPE html> <html> <head> <meta charset="utf-8"> <meta http-equiv="Content-Security-Policy" content="default-src 'none'; img-src 'self'"> <meta name="viewport" content="width=device-width, initial-scale=1"> <title>Thomas</title> </head> <body> <h1>Thomas</h1> <img src="Thomas.jpg" alt="Thomas"> <p>I write <em>software</em> and <strong>documentation</strong>.</p> <p>Text such as &lt;b&gt;this&lt;/b&gt; is shown as written.</p> </body> </html>

The interpreter's own form is built the way a composer builds a file: constant strings with the escaped texts between them. The Content-Security-Policy line tells the browser to run no script and load nothing but images from the same site, a second wall behind the first, since the page cannot hold script anyway.

Why it is safe
  • A journal names no file, and the guard refuses an instruction with any argument the language does not have, so a journal cannot point the interpreter anywhere. The page's name comes from the kernel's real uid, and its directory from the administrator's constraints.
  • The interpreter runs with the effective uid of http, not root, so even a fault in it reaches only what the web server's account can write.
  • The page's text cannot become markup, since the interpreter escapes it and writes every tag itself. The page cannot become server code either: its name always ends in .html, never .php or .htaccess.
  • The guard refuses a page or picture that has been made a symbolic link, and a directory reached through one, so a link cannot redirect the write to another file of http's.
  • The picture is published as given. The content check confirms its format, not what it shows, nor what its metadata says: a JPEG from a phone can carry the place it was taken. A composer that is to strip such metadata does so before placing the picture.
 Known problem The old compile script built the gate with -z relro, -z now and -fstack-protector-strong. Harmony's build has no flags for one namespace, so the gate is built without them. Execution stops at the first error and removes the temporary files of files not yet put in place, but an unlink that ran earlier in the journal stays done. The filesystem check and execution are separate, so a file can appear or change between them. Execution then fails on that instruction rather than acting on the change: a create whose file has appeared is refused by the hard link. A process whose real or effective uid is account A's can send signals to the gate, the guard and the interpreter, whose real uid is account A's, and so can kill the interpreter partway through a journal. The file language puts its files in place only after the last instruction, which keeps the window small, but an unlink already done, or a file already put in place, stays as it is. The gate checks the guard's verdict, not the guard's work: a guard that writes its approval line without reading the journal approves everything. The guard is installed code the application developer writes, and is to be tested as such. The gate stops an interpreter whose output breaks its rules, but what the interpreter did before then stays done. Road map
  1. Gates holding only the capabilities their instruction language needs, in place of setuid root.
  2. A language for installing programs, so that installing a gate, guard and interpreter is itself done through Man_In_Grey.
  3. Later, interpreters in a compiled language in place of Python.
 Possible future feature Namespace in place of index symbol

A symbol is now the index of the instruction that produces its value, so each instruction produces at most one value, and a value can be named only by a composer that holds its symbol. An alternative is to have instructions write their values into namespaces held by the journal interpreter, and later instructions read them by name.

A namespace is a dictionary. An instruction that produces values is given the namespace and the keys to write them under, and a later instruction names a namespace and a key where it needs a value. A key can name another namespace, so namespaces form a tree with one root namespace; a value is then named by its path, such as ("unbound" ,"file"), as a file is named by its path. The namespace is the scope, so the journal needs no scoping model of its own beyond the tree.

What the approach gives:

  • Several outputs from one instruction. An instruction can write each of its results under its own key, as a destructuring assignment does. An instruction that makes an account, for example, could give its uid, gid and home under three keys.
  • Values shared between composers. Composers run into one journal share no program variables, so one composer cannot hold another's symbol. A value written under a name one composer chooses can be read by another that knows the name.
  • A journal that reads by names. A printed journal would show what each value is, not only which instruction made it.

What the approach costs: the interpreter would hold state that instructions change, and the guard would have to know what a key holds at each point in the journal before anything runs. That stays as simple as it is with indices only under two rules: every key is written once, and every key is written before it is read. With those rules a path of keys can make its namespaces as it is first written, so no instruction for making namespaces is needed. Declarations, if they were wanted, would be instructions every instruction language carries.

A smaller step gives the first advantage alone: a symbol that names a field of its instruction's value, as {"symbol": 3 ,"field": "uid"}, keeps index symbols and lets one instruction produce several values.

Open question
  • Whether composers are given settings chosen when Man_In_Grey is run, such as a settings file every composer receives.
  • Whether constraints name files only exactly, as now, or also by pattern.
  • Where installed gates live, and how Man_In_Grey is told which gate a journal goes to.
 Change from the first version

The first version had configuration programs calling a planner, a plan, a fixed set of operations, copy, displace and delete, an inner executor, and one gate, man_in_grey_apply, that accepted --inner <file> from its caller. That option let any account in the group sudo run a program of its choosing with root's rights, without a password. The present design fixes the interpreter's path in its gate, moves the decision about which accounts can give journals into the constraints, raises an error in the composer on a wrong argument where the first version dropped the operation silently, replaces a scope fence that the gate's change of directory made ineffective with constraints naming each file, removes temporary files after a failure, and gives a second backup within one second a name of its own.
