Purpose

The Man_In_Grey tools were created to facilitate the controlled generation and installation of system configuration files, such as the files under /etc. These tools can be used, for example, to complete unprivileged account builds that require system configuration file changes, and to support programs that run from unprivileged accounts but, as a normal part of their operation, require configuration file changes.

With the Man_In_Grey approach, an application running with the real and effective uid of account A composes a journal, and that journal is given to a program called the gate. The gate is owned by account B and setuid, so that when invoked it runs with the effective uid of account B. Internally the gate first invokes a program called the guard to approve the journal. If approved the gate invokes another program called the interpreter, which plays the journal.

An application making use of Man_In_Grey can provide its own composer, guard, and interpreter. Consequently, each application that makes use of Man_In_Grey can have a different instruction language for the journal. Man_In_Grey merely provides the scaffolding.

This document is both the design of Man_In_Grey and the user manual, as Man_In_Grey is a programmer's tool.

All programs in Man_In_Grey are written with lead-in 'CLI' functions whose only job is to parse arguments and to format return values. Each CLI will call one or more functions to do the actual work. In this manner programs can be included as modules so as to reuse their helper functions, or to gain access to the main work functions.

Man_In_Grey provides an alternative to templates. In template systems an output file, such as a configuration file, is generated by a blank filling program. With Man_In_Grey the output file is written by interpreting a journal, and the journal is written by a composer.

There are problems with the method of filling in templates, for one it mixes data and control together: the content to be written, and the marks that say where to substitute. Thus templating is a form of in-band signaling. With in-band signaling, a content string can be identical to a control string, so data and control can alias, and there is no tight way to design the aliasing out. The typical workaround is to disallow control strings in the data, and to write each disallowed character as an escape sequence, where the escape is then itself control. Each level of nesting multiplies the escapes: an f-string that explains how to write f-strings escapes its braces has twice the number of escapes as the base f-string, and a document about this f-string escapes them again, to have 4 times the number, etc.

Man_In_Grey signals out of band. A composer is a program, so the logic that forms the output is code, with loops, conditions and lookups, rather than marks embedded in the output. Each instruction in the journal is then length delineated, so a scanner never has to examine content to find structure. A journal could even carry another journal as data, and no escaping would be required.

Note that Man_In_Grey replaces the template, but not the payload. Whatever limitations the payload has, it continues to have. For example if the payload is HTML, HTML requires escapes on a < in its text, Man In Grey has no say about this, rather the HTML interpreter does. However, no additional escapes will be required beyond what the HTML interpreter demands.

Real and effective uid

Each account has a number called its user id, or uid. Each file has an owner, noted with a uid. Each process is associated with two uids, its real uid and its effective uid. When a person logs in, the login program starts his shell with both uids set to that of his account, and every process started from the shell inherits them. In colloquial speech such processes are said to be owned by the person, or to run under his account. However, the two uids associated with a process can differ, so these colloquialisms are imprecise.

The effective uid determines a process's permissions. So for example when opening a file, the kernel compares the process's effective uid with a file's owner and permission bits to determine if the process is allowed to open the file. Among its other uses, the kernel lets a process send a signal to another process whose real uid, or saved uid, equals its own real or effective uid; explains signals and the saved uid, and how the gate stops account A signaling it.

A process inherits both uids from the process that invoked it, unless the program file it runs has its setuid permission bit set. In which case, the kernel then takes the effective uid from the file's owner instead, while the real uid remains inherited as before. A process therefore gets its effective uid in one of two ways: from the process that invoked it, or from the owner of a setuid program file. (Groups work the same way, with a real gid, an effective gid and a setgid bit, beside the supplementary groups, which are inherited unchanged.)

By convention, the gate is the only program of Man_In_Grey that can optionally be given the setuid bit. When the gate is not setuid, it inherits its effective and real uids from the program that invoked it. When it is setuid, it inherits its real uid from the program that invoked it, and it inherits its effective uid from its file owner. Thus, the gate process has reliable information directly from the kernel on who invoked it, as that is its real uid. It also has reliable information directly from the kernel on who owned its executable file, as that becomes its effective uid.

Due to this mechanism the effective uid for a setuid gate program can be different than the effective uid of the program that invoked it. In the chain of events of program A running and then invoking the gate, the effective uid in that thread of execution will start as the effective uid for program A, and then the effective uid will change to match the uid of the gate executable file owner. We can say that the effective uid change from A to B, where A is the invoking programs effective uid, an B is the owner of the gate executable file.

Instruction language

An instruction language is defined by the application developer and is built into the application. On the A side of the account divide, the composer writes the language by calling functions on the journal interface, one interface function per instruction. On the B account side of the divide, the guard checks the journal for correct syntax and that other constraints are met.

The instruction language is not specific to Man_In_Grey. An application that mounts home directories has a language of mount and unmount; one that manages accounts has a language for making and deleting them. Each gate starts the guard and the interpreter of one instruction language, and they refuse a journal written in another language. These coherency checks are due to the journal carrying the name of its language, and due to syntax checking of the constituent instructions passing.

A language can be made as narrow as its application. The narrower it is, the less a journal can say, and the less the guard has to rule out. The example language, , can name no file at all: what it writes, and where, is partially compiled in, and partially derived from the name of the invoking user account.

Data form Journal

A journal is a CBOR map of four entries:

The version of the journal's form, now 3. A guard or interpreter refuses a journal of another version. The name of the instruction language the journal is written in, such as emplace_bio. A guard and an interpreter refuse a journal in a language other than their own. When, on which host and by which account the journal was composed, the composer directory, and the composers that ran, in order. The instructions, in the order the composers placed them.

Each instruction is a map of three entries: name, which instruction it is; argument, a map holding all of the instruction's arguments, each keyed by argument name; and composer, the composer that placed it. Man_In_Grey's orchestrator records there the path of the composer's file, relative to the composer directory; an application that places instructions itself records what it chooses. The first four instructions of the journal in , decoded, and written in JSON notation:

{"name": "display_name", "argument": {"text": "Thomas"}, "composer": "bio.py"} {"name": "paragraph", "argument": {}, "composer": "bio.py"} {"name": "text", "argument": {"content": "I write ", "style": []}, "composer": "bio.py"} {"name": "text", "argument": {"content": "software", "style": ["emphasis"]}, "composer": "bio.py"}

An instruction that takes no arguments, such as paragraph, has an empty argument map. Arguments are given by name rather than by position, so the guard's wellformed check can require exactly the arguments an instruction takes: a text instruction carrying a third argument is refused, whatever that argument says.

An argument that is a symbol is the map {"symbol": <index>}, where the index locates the instruction that produces the value. In the account language of , the second instruction names the result of the first:

{"name": "make_account", "argument": {"user_name": "Thomas·www"}, "composer": "www.py"} {"name": "add_to_group", "argument": {"account": {"symbol": 0}, "group": "http"}, "composer": "www.py"}

Man_In_Grey's orchestrator runs the composers one after another into a single journal. Before it calls each composer's compose, it records that composer's path, relative to the composer directory, and every instruction placed during the call carries it. A journal composed from a directory of composers therefore shows which composer placed each instruction, and print shows it at the end of each line, which helps in finding the composer that placed a wrong one. The composer entry, like meta, is a note, not evidence: account A writes the whole journal, and could write anything there, so the guard and the interpreter never base a decision on either.

Symbol

A composer writes instructions, but it does not run them. When an instruction would produce a result when run, as for example an instruction that makes an account and returns its uid, the result does not exist yet at the time the composer runs. Hence, when an instruction is entered into the journal via the journal interface, the interface returns a symbol placeholder. The symbol is then used as an argument by the composer when it enters instructions that are given said result as an argument. In the current implementation a symbol is simply the index into the journal that locates an instruction. Thus, with the current implementation each instruction can have at most one result.

account = journal_iface.make_account("Thomas·www") journal_iface.add_to_group(account ,"http")

In this example account is a result symbol. The value of account will be 0, i.e. the index into the journal of the make_account instruction. The two instructions are of a language an application that manages accounts would define; the example language in has no instruction that produces a result.

Program Orchestrator

The orchestrator is a utility program provided with Man_In_Grey. The orchestrator calls one or more composer programs, then sends the resulting journal to a gate program. Like all processes, when the orchestrator program runs, it has a real and effective uid. When the orchestrator is run from a shell, these are both inherited from the shell, and are typically pointing to the login user. In any case, the composers that it invokes will then run with the same effective and real uids as the orchestrator. When the gate executable file has its setuid bit set, when the gate is invoke by the orchestrator, the gate will inherit its real uid from the orchestrator, and will take its effective uid from the gate's executable file owner.

The orchestrator finds the composers by file. Given a composer file, or a composer directory, it runs each file, and in each it calls one function, compose(prov ,journal_iface). To the orchestrator a composer is therefore a file: each composer is to be given a file of its own, and the file is to define exactly one function of that form. The file can define other functions as helpers of it, but the orchestrator calls none of them, and a second function meant as a composer is never run. Several composers are several files, and the order of the files in the composer directory, as describes, is the order they run in.

An application making use of Man_In_Grey can bypass the orchestrator and call the composers and gate on its own. When this happens the gate's real ID will be that of the application. For a setuid gate, its effective uid still comes from its file owner. Such an application calls its composer functions however it likes, as many to a module as it likes, since it does no search for them.

It is possible that the application is designed such that the executable file for the gate does not have its setuid bit set; or that it does have its setuid set, but the gate owner is the same as that of the orchestrator or that of the direct calling application. In such a case, the execution thread will keep the same real and effective uids the entire time it runs. In this mode the Man_In_Grey can not achieve anything the application could not have achieved on its own, but it still might be a convenient expression of the desired functionality. For example, as an alternative to template filling without effective uid changes.

Gate

The gate is compiled because Linux ignores the setuid bit on a script started with #!. Given no arguments, the gate prints its usage. Its command flags reports the gate's real and effective uid and gid with their names, whether they differ, the name of the gate's instruction language, and the paths of the guard and the interpreter.

> /usr/local/lib/Man_In_Grey/Man_In_Grey_gate/Man_In_Grey_emplace_bio_gate flags real.uid=2006 real.user_name=Thomas real.gid=2006 real.group_name=Thomas effective.uid=996 effective.user_name=http effective.gid=995 effective.group_name=http uid_differ=1 gid_differ=1 language=emplace_bio guard.path=/usr/local/lib/Man_In_Grey/Man_In_Grey/guard_emplace_bio.py interpreter.path=/usr/local/lib/Man_In_Grey/Man_In_Grey/interpreter_emplace_bio.py

Here Thomas asks the example language's gate, , installed setuid to the web server's account http: the real ids are his, and the effective ids are http's.

Th admit command takes the journal on standard input. There is an option check_only that will print check messages without doing anything. Without this option, when the gate is asked to admit a journal, it:

  1. puts every signal's disposition back to its default, turns off the interval timers, and clears the blocked mask, so no signal state the invoking program left can act later;
  2. opens /dev/null on any of descriptors 0, 1 and 2 the invoking program left closed, and closes every descriptor above 2, so nothing the invoking program opened reaches the guard or the interpreter;
  3. raises each resource limit that could stop the guard or the interpreter partway, file size and CPU time to unlimited, address space and data size to 1 GiB, stack size to 8 MiB, and open files to 64, as far as the hard limit allows, or past it when account B is root; and refuses when one stays too low;
  4. finds the guard and the interpreter at paths fixed when the gate is compiled, relative to the gate itself, so account A cannot name others;
  5. refuses unless the guard and the interpreter, and every directory above them, are owned by root or by account B, and writable by no other account;
  6. clears the environment, setting only PATH and LANG, sets the file mode mask to 077, marks the process not dumpable, and changes directory to /;
  7. records its real ids, account A's, in MIG_REAL_UID, MIG_REAL_GID and MIG_REAL_USER_NAME, for the guard and the interpreter;
  8. reads the journal from its standard input, up to 16 MiB;
  9. when accounts A and B differ, makes its real uid account B's, so the kernel refuses account A's signals, and ignores the signals a terminal sends; see ;
  10. starts /usr/bin/python3 -E -s -B on the guard, with the journal on its standard input, and goes on only when the guard approves the journal;
  11. starts the interpreter the same way, with the same journal, and takes the journal as played only when the interpreter writes its verdict line and exits 0.

The guard and the interpreter, before they import anything, each check that every module they load, the guard program among them, is owned by root or by account B, and writable by no other account. A module runs code when it is imported, so the check comes first.

The constraints, not the gate, decide which accounts can give a journal. The gate decides only whether the guard and the interpreter it would start can be trusted, and whether the guard approved the journal.

One gate per instruction language

Man_In_Grey's general gate is the library module Gate.lib.c, whose function Man_In_Grey_gate·Gate·run takes the name of the instruction language, the guard's path and the interpreter's path, and the command line. An instruction language's gate is a *.CLI.c of three lines that calls it with the three fixed. The gate of the example language:

#include "Gate.lib.c" int main(int argc ,char **argv){ return Man_In_Grey_gate·Gate·run("emplace_bio" ,"../Man_In_Grey/guard_emplace_bio.py" ,"../Man_In_Grey/interpreter_emplace_bio.py" ,argc ,argv); }

The general gate is curried, with its first three arguments supplied when the gate is compiled. Whoever invokes a gate can choose neither program it runs; if he could, he could give it a guard that approves everything. The language name holds no space and no control character, and the gate refuses to run when it does.

Output rule

Every line the guard and the interpreter write is copied to the person, marked guard: or interpreter:, and to the system log under the name Man_In_Grey_gate, beside the gate's own lines, marked gate:. The gate logs each journal's course itself, whatever the guard and the interpreter write: received, with account A, account B and the journal's size; isolated, when the gate gives up account A; then approved or refused; then interpreting; then interpreted or failed. A line breaks the gate's rules when it is not UTF-8, or holds a control character (C0, DEL or C1), or is longer than 4096 bytes, or is one line more than 2000; the gate then stops the program and refuses the journal. Unicode is otherwise welcome. The guard writes any control character it quotes as \u{XXXX}, and the example language's wellformed check refuses any text that holds one.

Transport

A journal reaches its interpreter by starting the interpreter's gate with the journal on standard input. Since a journal is data, it could travel other ways, such as over a Unix domain socket to an interpreter already running, which would learn account A through SO_PEERCRED. Man_In_Grey does not do this. It is the mechanism a program that receives requests is built with, not such a program itself.

Guard

Accounts exist to limit what programs can do. The guard decides, before anything runs with the effective uid of account B, whether the work account A asks for is allowed: it reviews the journal and checks it against a set of constraints, and approves the journal only when every constraint is met.

The kernel tells the gate which account invoked it, as the real uid, and the gate passes it on, so the guard knows it also. The kernel does not say which program invoked the gate. As the guard invocation is compiled into the gate, the guard can know the provenance of the journal from the point it was given to the gate, but not before that.

Two checks are needed by nearly every guard, whatever its instruction language. The first is that the journal is well formed: that it decodes, names only instructions of its language, and gives each instruction the arguments it takes, of the right kinds. This check carries knowledge of the instruction syntax, so it belongs to the instruction language. The second is who account A is. The gate had account A's uid from the kernel, as its real uid, and records it for the guard before giving it up, ; the real gid and supplementary groups the gate inherited from the invoking program stay account A's, and the guard reads them from the kernel. Account A cannot misstate any of them. A guard can therefore allow a journal from the accounts it names, or from the members of a group, as its constraints decide.

The other checks a guard makes belong to its instruction language. The example language's four checks are in .

Constraint predicate

A guard's constraints are code. The guard is a Python program, written for one application, so its constraints are Python functions written at the top of the guard itself, where they go with it, and no language for expressing constraints is needed. Each is a constraint predicate, named in the manner of is_allowed_account(user_name) or is_allowed_open(directory ,name ,mode ,owner ,permission), and the guard refuses a journal when one does not answer True. A predicate can compare with a list, ask whether an account is in a group, or anything else Python can say. The predicates sit between the lines # constraints begin and # constraints end, so that install_gate can put in an administrator's and keep them when the guard is installed again. As promoted with Man_In_Grey, they refuse every account.

Some constraints recur from one guard to the next, and the library module Constraint.py holds them, for a guard's predicates to call:

The account is in the group by the group database: listed as a member in /etc/group, or having it as its primary group. The gate's real gid or supplementary groups include the group. These are what the invoking program held, passed on by the kernel, so an account that joined the group after its session began does not have it yet, though is_group_member already says yes. The path is the directory or lies within it, both absolute and in normal form. The permission sets no bit the limit does not: 0o600 is within 0o644, and 0o4755, setuid, is within neither 0o644 nor 0o755.

The guard checks and imports its modules, Constraint.py among them, only after its predicates are defined, and calls the predicates only after that, so a predicate can call Constraint.is_group_member by name, though the import comes later in the file. Code at the top level of the constraints runs before the ownership check, so the constraints hold only definitions, and imports of the standard library at most. The interpreter imports the guard program, for what execution needs from its constraints.

Verdict

A guard reads the journal on its standard input. Its standard error is for the person: one line per finding, as <tag>: <message>, the first two name: and version:, then such lines as check_passed: wellformed or constraint_broken: <what is wrong>. Its standard output is for the verdict alone. A guard approves a journal by writing exactly one line there, guard <language> check passed, with the language name the gate has compiled in, and exiting 0. The gate takes the journal as approved on that line and that status together, and on nothing else, and only then admits it to the interpreter; a guard that refuses exits 1, and one that cannot check exits 2.

The verdict travels out of band from the findings. A finding quotes the journal, a file name for instance, and goes to standard error, so nothing in a journal can put a line on standard output. A crash cannot approve a journal either: an uncaught Python exception exits 1, and a guard that dies leaves no verdict.

Interpreter

The gate starts the interpreter only after the guard has approved the journal, with the effective uid of account B and the same journal on its standard input. Generally the interpreter does not check the constraints as that is the guard's work, but some checks will naturally occur as part of interpretation. Where useful the guard program module can be included so as to pull in the helper functions.

The gate logs when a journal is received, approved, and interpreted. The interpreter writes to standard error, as <tag>: <message>, the highlights of what it does, as its developer chooses them. Its standard output is for its verdict alone, as the guard's is: when it has played the whole journal, it writes exactly one line there, interpreter <language> journal played, and exits 0. The gate takes the journal as played on that line and that status together; an interpreter that exits 0 without it, having returned early or not being the program it should be, is logged as failed. Otherwise its exit status is 1 when it stopped partway, and 2 when the journal could not be read or is not well formed.

The verdict line says only that the interpreter reached its end. It cannot undo what an interpreter did before failing, and it is the interpreter's own claim, not evidence that what it did was right.

Execution stops at the first error. What the interpreter did before then stays done, except what its instruction language undoes; for the example language, see . Playing a journal as a transaction is a possible future feature; see .

Isolation from account A

The aim is that a journal be played as a transaction: either all of it takes effect, or none of it does, with nothing in between. Man_In_Grey is not there yet, since an interpreter can still fail partway, as discusses. But no interpreter can be transactional while account A can stop it partway, and until this design, account A could: by sending a signal to the gate, the guard or the interpreter, or by having arranged before the gate started for a signal to arrive later. This chapter explains signals, the uid that lets a setuid program give up account A, and what the gate does so that once it has the journal, account A can no longer interrupt it.

Signal

A signal is a small message the kernel delivers to a process: a number, such as SIGTERM, asking it to end, SIGINT, sent by Ctrl-C, or SIGKILL. One process sends a signal to another with the system call kill; the kernel also sends signals of its own, as when a timer expires or a process writes to a pipe nobody reads.

Sending a signal is two steps. First the kernel decides whether the sender may signal the target at all: a process may signal another when the sender's real or effective uid equals the target's real uid or its saved uid, described below, or when the sender is root. If neither holds, kill fails with EPERM, "Operation not permitted", and no signal exists. Only then, second, is the signal delivered, and the target's disposition for that signal decides what happens: the default action, which for most signals ends the process; ignoring it; or running a handler the program installed. Two signals, SIGKILL and SIGSTOP, can be neither handled nor ignored, so a handler can never protect a process from them. Only the first step can.

A setuid gate starts with account A as its real uid, so it passes the first step for account A. Account A could therefore end the gate, the guard or the interpreter with SIGKILL at any moment, the interpreter halfway through a journal included.

Saved uid

A process holds three uids, not two: real, effective, and saved. When a setuid program is executed, the kernel sets the effective uid to the file's owner and copies it into the saved uid; the real uid stays as inherited. A setuid gate owned by account B therefore starts holding account A as its real uid, and account B as its effective and saved uids.

A process may rearrange its uids among the ones it already holds, without privilege, but it cannot take a uid it does not hold. The call setreuid(real ,effective) may set the real uid to the current real or effective uid, and when it changes the real uid it sets the saved uid to the new effective uid. So a setuid gate may call setreuid(B ,B), making all three of its uids account B's. It gains nothing by this, since it already acts with account B's rights; it only gives up its connection to account A, and once given up, account A cannot be taken back. Only a process with CAP_SETUID, in practice root, may set a uid it does not hold, which is how login starts a shell under the account a person signed in to.

The saved uid exists so that a setuid program can drop its rights for a while and take them back: it sets its effective uid to its real uid, does some work on the person's behalf, and returns to the saved uid. Man_In_Grey uses the same rules the other way, to drop account A for good.

Isolating the gate

Once the gate has read the whole journal, and before it starts the guard, it makes its real uid account B's, as above. From then on account A matches neither the gate's real uid nor its saved uid, and the kernel refuses account A's signals at the first step, SIGKILL and SIGSTOP included. The guard and the interpreter are started after this, and inherit all three uids. The gate logs the moment:

gate: received: real uid 2006 (Thomas), effective uid 996 (http), journal of 1857 bytes gate: isolated: real uid now 996 (http); account A can no longer signal the gate

Here is account A trying, after that line, to stop the example language's gate, installed setuid to http. The guard was slowed for the demonstration so there was time to try:

gate pid 693 Uid: 996 996 996 996 kill: (693) - Operation not permitted kill: (693) - Operation not permitted kill: (693) - Operation not permitted

The Uid line from /proc/693/status gives the real, effective, saved and file-system uids, all http's; the three refusals are SIGKILL, SIGSTOP and SIGTERM. The run went on to place the page.

Waiting until the journal is read costs nothing. Until then the gate has done nothing that would need undoing, so account A interrupting it earlier only stops a run that has not begun.

Signal state that outlives exec

Refusing account A's signals is not enough by itself, since account A could arrange beforehand for a signal to arrive after the switch. Three pieces of a process's signal state survive exec, so the program that invokes the gate can leave them behind:

A timer set with alarm or setitimer keeps running in the gate. When it expires, the kernel sends SIGALRM, SIGVTALRM or SIGPROF to the gate itself, with no question of who set the timer, so the switch does not stop it. Each ends the process by default: a timer set to expire partway through would end the interpreter there. The invoking program can block a signal and send it, so it waits, pending. Both survive exec, and the signal would be delivered whenever it came to be unblocked. A signal set to be ignored stays ignored. Ignoring SIGCHLD, for one, makes the kernel discard a child's exit status, so the gate could not learn how the guard ended.

The gate therefore settles its signal state first, before anything else, as it settles its descriptors and resource limits: it puts every signal's disposition back to its default, turns off the three interval timers, and clears the blocked mask. Clearing the mask delivers any signal already pending, then and there, while the gate has done nothing. A process that goes past its limit of CPU time or of file size is sent SIGXCPU or SIGXFSZ; the gate raises those limits at its start, and refuses to run when it cannot.

The test tester/authored/emplace_bio starts the gate from a process that leaves each kind behind: a timer set to send SIGALRM fifty milliseconds in, an ignored SIGCHLD, and a blocked, pending SIGTERM. With the gate settling its signals, the first two runs place the page, and the third ends at once, having changed nothing. With the settling step taken out, the timer ends the gate partway, the ignored SIGCHLD makes it refuse, and the pending SIGTERM stays blocked, unnoticed.

The terminal

A terminal sends signals of its own to the programs running in its foreground: SIGINT for Ctrl-C, SIGQUIT for Ctrl-\, SIGTSTP for Ctrl-Z, SIGTTIN and SIGTTOU when a program in the background reads it or, if the terminal is so set, writes it, and SIGHUP when it is closed. These come from the terminal driver, not from a process, and are not checked against uids. So when it isolates itself, the gate also ignores all six; the guard and the interpreter inherit that. No key on a terminal sends SIGKILL or SIGSTOP.

Pressing Ctrl-C, Ctrl-\ and Ctrl-Z during a run of the example ended the orchestrator, account A's own program, by SIGQUIT; the gate, the guard and the interpreter went on, and the page was placed. The gate also ignores SIGPIPE, so a reader of its output that has gone away does not end it; its lines still reach the system log.

One signal still reaches the gate from account A: the kernel lets any process in the same session send SIGCONT, whatever its uid. SIGCONT only resumes a stopped process, and account A can no longer stop the gate, so it does nothing.

Who account A is, afterwards

Once the gate has given up account A, the kernel no longer says who account A is: the guard and the interpreter find account B as their real uid. The gate records account A before giving it up, in MIG_REAL_UID, MIG_REAL_GID and MIG_REAL_USER_NAME, having first cleared the environment, so the variables say what the gate says and nothing account A put there. The guard and the interpreter read account A from them, and refuse to work when the uid and the user name do not name the same account. Knowledge of account A therefore rests on the gate, which had it from the kernel.

The gate gives up only the uid. Its real gid and supplementary groups stay account A's, so Constraint.has_real_group still answers for account A's groups.

What isolation does not give
  • Before the journal is read, account A can still stop the gate. Nothing has been done, so nothing is lost.
  • When accounts A and B are the same, there is nothing to isolate, and the gate does not; the person can interrupt his own run, which has no more than his own rights.
  • Root can signal any process. Root is trusted.
  • The interpreter can still fail partway on its own. Isolation removes account A as a cause, which a transactional play needs, but does not make the play transactional; see .

Writing a composer

Composers are kept in a composer directory, named composer in the examples here. Every file in it is a composer, a Python file defining compose(prov ,journal_iface); notes such as a README belong a directory up. Its subdirectories are namespaces for the author. They set the order the composers run in: depth first, in order of name at each level, files and subdirectories together, by Unicode code point, so capital letters come before small ones. A composer's place says nothing else; what a composer does is said by the instructions it places.

A composer runs with the orchestrator's uids, which are normally account A's, and so with account A's rights. If another account could change a composer, or add one to a composer directory, that account's code would run with account A's rights, and its instructions would reach the gate in account A's name. Every composer, and every directory from / down to it, is therefore to be owned by account A or by root, and writable by no other account.

This ownership protects account A, not account B, and the gate cannot enforce it. The gate is given a journal, never the program that made it, and anything it is told about the composers comes from account A. To the gate and the guard, every journal is account A's, whatever made it. Composer ownership is therefore a convention, kept by whoever installs an application's composers. Man_In_Grey's orchestrator keeps it for its own runs: before running any composer it makes the check, and it refuses a symbolic link in a composer directory. An application that acts as its own orchestrator keeps the convention itself. To run a composer someone else wrote, review it and copy it into your own composer directory.

# composer/bio.py def compose(prov ,journal_iface): journal_iface.display_name("Thomas") journal_iface.paragraph() journal_iface.text("I write software." ,[])

This composer writes in the example language; shows a whole one. compose is given prov, which says where the composer is:

The composer's own file name less .py, for a composer named for the file it writes. The name of account A. The composer directory, the composer's path absolute and relative to it, the directory holding the composer, and the working directory of the run.

Man_In_Grey orchestrate <path> runs the one composer in a composer file, or every composer in a composer directory. No option given to Man_In_Grey reaches compose; a composer's settings are written in the composer itself. The journal_iface a composer is given is that of the gate's instruction language: the orchestrator asks the gate for its flags, and loads the module named for its language, EmplaceBioLanguage.py for emplace_bio.

Running

A run that changes files is best preceded by two that do not. The first shows the journal while nothing has left the person's account; the second has the guard check the journal, and the gate stop before the interpreter:

Man_In_Grey orchestrate composer gate <gate> print compose_only Man_In_Grey orchestrate composer gate <gate> check_only Man_In_Grey orchestrate composer gate <gate> Run the composer in a composer file, or every composer in a composer directory, and invoke the gate with the journal. The gate to invoke, which also sets the instruction language the composers write in. Required: the orchestrator has no gate of its own. Print the journal after composing. Stop after composing; nothing reaches the gate. Have the gate run the guard and not the interpreter.

The command and its path come first, then the gate, and the options follow, as plain words; given no arguments, Man_In_Grey prints its help, and so does the gate. The exit status is 0 when the run did what it was asked; 1 when the guard refused the journal or an instruction failed to execute; and 2 when the run could not start, a composer failed or was refused, or the gate, guard or interpreter could not run or broke the gate's rules. The guard's and interpreter's lines are also in the system log; on a system with journald, journalctl -t Man_In_Grey_gate shows them.

Installing a setuid gate

A setuid gate and everything its guard and interpreter load are to be owned by root or by account B, in directories no other account can write, and the gate, the guard and the interpreter check this on every run. A Harmony consumer/ directory is owned by the person who promoted into it, so a setuid gate there refuses to run, and so does root running the gate there. Installing an instruction language's gate, guard and interpreter is therefore a step of its own, done with root's rights by the Man_In_Grey administrator, the person who installs Man_In_Grey and the applications that use it.

The installation is done by install_gate, which is promoted beside Man_In_Grey and is run by root. The administrator runs it through Man_In_Grey:

consumer/Man_In_Grey/Man_In_Grey install <gate> owner <account> [group <group>] into <directory> [constraints <file>]

Run by root, Man_In_Grey install runs install_gate directly. Run by any other account, such as a developer account without sudo, it runs it through su, which asks for root's password; it first makes a constraints file's path absolute, as root's shell starts in another directory. Root can also run install_gate install itself, with the same arguments. Either way the administrator runs, with root's rights, the install_gate and the files of the tree he names, so he is to install only a tree he has reviewed.

It copies Man_In_Grey/ and the one gate named from Man_In_Grey_gate/ into the directory, side by side, as the gate's compiled paths expect. Every file and directory it installs is owned by root and writable by no other account, except the gate, which it gives to account B, the owner account named, and to a group, and then makes setuid and setgid. The order matters, since changing a file's owner clears its setuid and setgid bits. The gate's mode is 6755: the mode 755 with the setuid bit, 4000, and the setgid bit, 2000, added. The setgid bit gives the gate the group as its effective gid, and an interpreter makes its files with the effective gid's group: only root can give a file away, so an interpreter whose effective uid is that of an account B other than root makes files that account B owns, in that group. The group is account B's own unless group <group> names another, such as a group the web server reads through. When account B and the group are both root's, the setgid bit changes nothing, and the mode is 4755.

With constraints <file>, a Python file of predicates, install_gate puts them between the constraint marks of the gate's guard. Without it, the constraints of a guard already installed are kept, so installing again brings a new guard and keeps the administrator's constraints; a first installation gets the guard's as promoted, which refuse every account. The constraints of every other installed guard are kept too. install_gate refuses a directory that is not absolute, that an account other than root owns or can write, or that is on a file system mounted nosuid, where the kernel ignores the setuid and setgid bits, as it does on removable drives and some separately mounted /home directories. It ends by printing the installed gate's flags, as root sees them: real uid and gid root's, effective uid account B's, effective gid the group's. Promotion replaces files and sets neither the owner nor the setuid bit, so the installation is redone after each promotion that changes the gate, the guard or the interpreter. The installation is a candidate for Man_In_Grey itself, once there is a language for installing programs.

Testing

The tester's test tester/authored/emplace_bio copies the promoted Man_In_Grey into its scratchpad directory, puts constraints of its own at the top of the copy's guard, and runs the copy through the example language's gate, not setuid, so accounts A and B are the same. The gate checks ownership on every run, so the test makes its copy writable by its owner alone, and every directory from / down to the scratchpad directory is to be writable by no account but its owner too.

It checks thirty-two things. A page with every style and with text that looks like markup is compared with expected/page.html, and its picture with the one given. A later run with a JPEG places it and removes the PNG, and a run with no picture removes the JPEG. A check_only run changes nothing. Seven journals are then made without the journal interface and given to the gate directly, as a program other than the orchestrator could: one whose text instruction carries a file name, one with a style the language does not have, one with text before any paragraph, one with an SVG picture, one with more text than its constraints allow, one from an account they do not allow, and one for a page that has been made a symbolic link. Each is refused by the check that is to refuse it, and changes nothing. Last, the gate is started three times from a process that leaves signal state behind, as describes:

authored/emplace_bio/run test authored/emplace_bio/run clean

The tester's smoke test, authored/smoke/run test, exercises the gate, the guard and the interpreter through a language of its own that is not for use on a system.

Example: emplace_bio

A host publishes a bio page for each of the accounts it allows, at /srv/http/bio/<user_name>.html, with the account's picture beside it. The directory belongs to the web server's account, http on Arch and www-data on Debian, so a person cannot write his page there himself. He writes a composer giving his display name, his text and his picture, and runs Man_In_Grey with the gate Man_In_Grey_emplace_bio_gate, which the administrator has installed setuid to the web server's account. The interpreter then runs with the effective uid of http, and builds the page.

Here account B is not root, and the gate stands between two ordinary accounts. The example is made so that a reader can see each step is safe: a person can change only his own page, and only to a page made of his text and picture.

The instruction language The page's title and heading. Given once. Starts a paragraph. A run of text in the current paragraph. style is a list drawn from strong, emphasis, underline and strikethrough; an empty list is plain text. The bytes of a PNG or JPEG image. At most once.

No instruction names a file. The page's file names come from the user name of the real uid, which the kernel gives the guard and the interpreter, so a person can write only his own page. The directory comes from page_directory() among the guard's constraints, which the administrator writes. A journal describes the whole page: a run that gives no picture removes the picture an earlier run placed.

Decoration travels out of band. A run's styles are a list beside its text, not marks in it, and the interpreter turns each style into one fixed tag with no attribute: <strong>, <em>, <u> and <s>, nested in that order. It writes the rest of the page from a fixed form, and escapes every text it is given, so nothing a person gives becomes markup. There is nothing to sanitize: an attribute such as onload, or a <script> element, cannot be expressed in the language.

The composer

The composer is Thomas's own program, running with his uid. It holds the text in code and reads the picture from beside the composer directory:

# composer/bio.py from pathlib import Path DISPLAY_NAME = "Thomas" BIO = [ [("I write " ,[]) ,("software" ,["emphasis"]) ,(" and " ,[]) ,("documentation" ,["strong"]) ,("." ,[])] ,[("Text such as <b>this</b> is shown as written." ,[])] ] def compose(prov ,journal_iface): journal_iface.display_name(DISPLAY_NAME) for paragraph in BIO: journal_iface.paragraph() for content ,style in paragraph: journal_iface.text(content ,style) journal_iface.picture((Path(prov.composer_root_dpath).parent / "picture.jpg").read_bytes())

A composer could as well read a file in a notation its author likes, such as *emphasis*, and turn it into runs. That conversion runs with the person's own uid, so a mistake in it stays on his side; the gate only ever receives runs and style names.

The constraints

The administrator writes the guard's constraints in a file, here bio_constraint.py, and install_gate puts them at the top of the installed guard_emplace_bio.py:

def is_allowed_account(user_name): return user_name in ("Thomas" ,"Alice") def is_allowed_text_size(byte_count): return byte_count <= 8192 def is_allowed_picture_size(byte_count): return byte_count <= 1 << 20 def page_directory(): return "/srv/http/bio"

One set of constraints serves every account, since the page's name follows from the account. is_allowed_text_size is given the bytes of the display name and text together. page_directory is not a predicate: the guard checks that it gives an absolute directory, and the interpreter places the pages there. To give a page to every member of a group instead:

def is_allowed_account(user_name): return Constraint.is_group_member(user_name ,"bio") The guard Only the four instructions, with exactly their arguments; one display name; at most one picture; text only within a paragraph, and no paragraph without text; every style one of the four, none twice; no control character in any text. is_allowed_account allows account A; is_allowed_text_size and is_allowed_picture_size allow the text and the picture; page_directory() gives an absolute directory. The picture begins with the signature of a PNG or a JPEG file. SVG is refused on purpose: it is a document that can hold script, and run it when opened by itself. The directory exists, is reached through no symbolic link, and can be written by the effective uid's account; the account's page and pictures, where they exist, are regular files.

The filesystem check asks whether the effective uid can write the directory. Python's os.access, like the system call access under it, answers for the real uid unless asked with effective_ids=True, since it was made for setuid programs to ask what the person who ran them could do.

The interpreter

The interpreter writes the picture and the page to temporary files in the directory, gives each permission 0644, and renames each into place, then removes a picture the page no longer shows. The files are owned by http, the effective uid that made them. The page Thomas's composer gives:

<!DOCTYPE html> <html> <head> <meta charset="utf-8"> <meta http-equiv="Content-Security-Policy" content="default-src 'none'; img-src 'self'"> <meta name="viewport" content="width=device-width, initial-scale=1"> <title>Thomas</title> </head> <body> <h1>Thomas</h1> <img src="Thomas.jpg" alt="Thomas"> <p>I write <em>software</em> and <strong>documentation</strong>.</p> <p>Text such as &lt;b&gt;this&lt;/b&gt; is shown as written.</p> </body> </html>

The interpreter's own form is built the way a composer builds a file: constant strings with the escaped texts between them. The Content-Security-Policy line tells the browser to run no script and load nothing but images from the same site, a second wall behind the first, since the page cannot hold script anyway.

Why it is safe
  • A journal names no file, and the guard refuses an instruction with any argument the language does not have, so a journal cannot point the interpreter anywhere. The page's name comes from account A's user name, which the gate had from the kernel as its real uid, and its directory from the administrator's constraints.
  • Once it has the journal, the gate gives up account A, so Thomas cannot stop the guard or the interpreter partway, and a page is never left half placed by him.
  • The interpreter runs with the effective uid of http, not root, so even a fault in it reaches only what the web server's account can write.
  • The page's text cannot become markup, since the interpreter escapes it and writes every tag itself. The page cannot become server code either: its name always ends in .html, never .php or .htaccess.
  • The guard refuses a page or picture that has been made a symbolic link, and a directory reached through one, so a link cannot redirect the write to another file of http's.
  • The picture is published as given. The content check confirms its format, not what it shows, nor what its metadata says: a JPEG from a phone can carry the place it was taken. A composer that is to strip such metadata does so before placing the picture.
 Known issue The gate checks the guard's verdict, not the guard's work: a guard that writes its approval line without reading the journal approves everything. The guard is installed code the application developer writes, and is to be tested as such. When an interpreter crashes, fails, or breaks the gate's output rules partway through a journal, what it did before then stays done, and the gate can only log the failure. Playing a journal as a transaction is on the road map. The gate learns only how the interpreter ended, and what it wrote. Its verdict line says it reached its end; whether the files it made are what the journal meant is the interpreter's own claim, so the interpreter, like the guard, is installed code the application developer writes, and is to be tested as such. Road map
  1. Gates holding only the capabilities their instruction language needs, in place of setuid root.
  2. A language for installing programs, so that installing a gate, guard and interpreter is itself done through Man_In_Grey.
  3. Transactional play: a journal takes effect wholly or not at all; see .
  4. Later, interpreters in a compiled language in place of Python.
 Possible future feature Least privilege

A setuid gate owned by root gives the interpreter every one of root's rights. Root's rights are a set of about forty separate capabilities, among them CAP_DAC_OVERRIDE, to ignore file permissions; CAP_CHOWN, to change owners; CAP_SYS_ADMIN, to mount; and CAP_SETUID, to become another uid. The design is to give each such gate only the capabilities its instruction language needs.

setcap stores chosen capabilities in a program file's extended attributes. A process running that file holds them while its real and effective uid stay account A's. Capabilities are normally lost when a program execs one whose file holds none, as the gate does when it starts Python; the gate keeps them by raising them as ambient capabilities first, which survive the exec. A gate for a language that places files owned by other accounts would then be able to write files and change owners, and nothing else. The gain is uneven: CAP_SYS_ADMIN, needed for mounting, is nearly root by itself.

Namespace in place of index symbol

A symbol is now the index of the instruction that produces its value, so each instruction produces at most one value, and a value can be named only by a composer that holds its symbol. An alternative is to have instructions write their values into namespaces held by the journal interpreter, and later instructions read them by name.

A namespace is a dictionary. An instruction that produces values is given the namespace and the keys to write them under, and a later instruction names a namespace and a key where it needs a value. A key can name another namespace, so namespaces form a tree with one root namespace; a value is then named by its path, such as ("unbound" ,"file"), as a file is named by its path. The namespace is the scope, so the journal needs no scoping model of its own beyond the tree.

What the approach gives:

  • Several outputs from one instruction. An instruction can write each of its results under its own key, as a destructuring assignment does. An instruction that makes an account, for example, could give its uid, gid and home under three keys.
  • Values shared between composers. Composers run into one journal share no program variables, so one composer cannot hold another's symbol. A value written under a name one composer chooses can be read by another that knows the name.
  • A journal that reads by names. A printed journal would show what each value is, not only which instruction made it.

What the approach costs: the interpreter would hold state that instructions change, and the guard would have to know what a key holds at each point in the journal before anything runs. That stays as simple as it is with indices only under two rules: every key is written once, and every key is written before it is read. With those rules a path of keys can make its namespaces as it is first written, so no instruction for making namespaces is needed. Declarations, if they were wanted, would be instructions every instruction language carries.

A smaller step gives the first advantage alone: a symbol that names a field of its instruction's value, as {"symbol": 3 ,"field": "uid"}, keeps index symbols and lets one instruction produce several values.

Group and setgid

The gate gives up account A's uid when it isolates itself, , but not account A's real gid or supplementary groups. Signals are permitted by uid alone, so the groups do not let account A interrupt it, and keeping them lets a constraint ask about account A's groups with Constraint.has_real_group. Three pieces of work remain:

  • Recording account A's groups. If the gate gave up account A's gids too, with setregid and setgroups, so that nothing of account A's identity remained in the process, it would record the groups first, as it records the uid, and has_real_group would read them from the record.
  • A constraint by group. Constraint.is_group_member and has_real_group let a guard admit the members of a group, but the example's guard admits accounts by name; a group, such as bio, is the more natural grant on a real host, and the example could show it.
  • Which group the interpreter's files take. A setgid gate makes its files in the group install_gate gives it. A language that places files for several groups would need the interpreter to set each file's group, which an account B other than root can do only to the groups account B belongs to.
 Checking at the moment of acting

The guard checks the files a journal will touch before the interpreter runs, so they can change in between. Changing them takes write access to their directory, and an account with that access could change them without the gate, so the gap gives no account anything it did not already have. It would still be better closed, so that what was checked is what is acted on.

File locks are the obvious tool, but on Linux they bind only programs that take them: flock and fcntl locks are advisory, and the kernel dropped mandatory locking in version 5.15. The way to close the gap is for the interpreter to make the filesystem checks itself, on the very directory descriptors it then writes through, as the example language's interpreter already does in part by opening its directory without following a symbolic link and renaming into place within it.

Transactional play on Btrfs

Execution now stops at the first error, and what the interpreter did before then stays done, except what its instruction language undoes. A journal would better be played as a transaction: either every instruction takes effect, or none does. Btrfs gives a way to do this for every instruction language, without each language undoing its own work.

A Btrfs subvolume is a directory tree that can be snapshotted. Making a snapshot takes about as long as making a directory, whatever the size of the tree, because the snapshot shares every block with its source; a block is copied only when one side writes it. Before playing a journal, the interpreter would snapshot each subvolume the journal writes in. When the play succeeds, it deletes the snapshots. When the play fails, it puts back each file it changed from the snapshot, then deletes the snapshots. It knows which files those are, since it touched them.

Putting back files one at a time is the general case. A running system cannot replace the subvolume it runs from, such as the one holding /etc, so there the rollback is a restore of each changed file, each in one step, by the same rename the example language uses to put a file in place. Where the destination is a subvolume of its own that is not mounted separately and that no program depends on keeping open, such as a web server's page directory, the interpreter could instead play the journal into a snapshot and then exchange the snapshot and the subvolume in one call, renameat2 with RENAME_EXCHANGE, so the whole change appears at once or not at all. Whether Btrfs allows that exchange between subvolumes is to be confirmed before the design relies on it.

The cost is privilege. Making a snapshot needs ownership of the subvolume, or root, and write access to the directory the snapshot goes in. Deleting one needs CAP_SYS_ADMIN, unless the file system is mounted with user_subvol_rm_allowed. A gate whose account B is not root would need the second, and a gate holding only the capabilities its language needs would need the first, which is nearly root by itself. On other file systems the play stays as it is, and a language undoes its own work where it can, as the example language does by writing its files to temporary names and renaming each into place.

 Change from the first version

The first version had configuration programs calling a planner, a plan, a fixed set of operations, copy, displace and delete, an inner executor, and one gate, man_in_grey_apply, that accepted --inner <file> from its caller. That option let any account in the group sudo run a program of its choosing with root's rights, without a password. The present design fixes the interpreter's path in its gate, moves the decision about which accounts can give journals into the constraints, raises an error in the composer on a wrong argument where the first version dropped the operation silently, replaces a scope fence that the gate's change of directory made ineffective with constraints naming each file, removes temporary files after a failure, and gives a second backup within one second a name of its own.
