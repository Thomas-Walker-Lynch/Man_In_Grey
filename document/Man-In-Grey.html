Purpose

The Man-In-Grey tools were created to facilitate the controlled generation and installation of system configuration files, such as the files under /etc. These tools can be used, for example, to complete unprivileged account builds that require system configuration file changes, and to support programs that run from unprivileged accounts but, as a normal part of their operation, require configuration file changes.

With the Man-In-Grey approach, an application running with the real and effective uid of account A composes a journal, and that journal is given to a program called the gate. The gate is owned by account B and setuid, so that when invoked it runs with the effective uid of account B. Internally the gate first invokes a program called the guard to approve the journal. If approved the gate invokes another program called the interpreter, which plays the journal.

An application making use of Man-In-Grey can provide its own composer, guard, and interpreter. Consequently, each application that makes use of Man-In-Grey can have a different instruction language for the journal. Man-In-Grey merely provides the scaffolding.

This document is both the design of Man-In-Grey and the user manual, as Man-In-Grey is a programmer's tool.

All programs in Man-In-Grey are written with lead-in 'CLI' functions whose only job is to parse arguments and to format return values. Each CLI will call one or more functions to do the actual work. In this manner programs can be included as modules so as to reuse their helper functions, or to gain access to the main work functions.

Man-In-Grey provides an alternative to templates. In template systems an output file, such as a configuration file, is generated by a blank filling program. With Man-In-Grey the output file is written by interpreting a journal, and the journal is written by a composer.

There are problems with the method of filling in templates, for one it mixes data and control together: the content to be written, and the marks that say where to substitute. Thus templating is a form of in-band signaling. With in-band signaling, a content string can be identical to a control string, so data and control can alias, and there is no tight way to design the aliasing out. The typical workaround is to disallow control strings in the data, and to write each disallowed character as an escape sequence, where the escape is then itself control. Each level of nesting multiplies the escapes: an f-string that explains how to write f-strings escapes its braces has twice the number of escapes as the base f-string, and a document about this f-string escapes them again, to have 4 times the number, etc.

Man-In-Grey signals out of band. A composer is a program, so the logic that forms the output is code, with loops, conditions and lookups, rather than marks embedded in the output. Each instruction in the journal is then length delineated, so a scanner never has to examine content to find structure. A journal could even carry another journal as data, and no escaping would be required.

Note that Man-In-Grey replaces the template, but not the payload. Whatever limitations the payload has, it continues to have. For example if the payload is HTML, HTML requires escapes on a < in its text, Man-In-Grey has no say about this, rather the HTML interpreter does. However, no additional escapes will be required beyond what the HTML interpreter demands.

Real and effective uid

Each account has a number called its user id, or uid. Each file has an owner, noted with a uid. Each process is associated with two uids, its real uid and its effective uid. When a person logs in, the login program starts his shell with both uids set to that of his account, and every process started from the shell inherits them. In colloquial speech such processes are said to be owned by the person, or to run under his account. However, the two uids associated with a process can differ, so these colloquialisms are imprecise.

The effective uid determines a process's permissions. So for example when opening a file, the kernel compares the process's effective uid with a file's owner and permission bits to determine if the process is allowed to open the file. Among its other uses, the kernel lets a process send a signal to another process whose real uid, or saved uid, equals its own real or effective uid; explains signals and the saved uid, and how the gate stops account A signaling it.

A process inherits both uids from the process that invoked it, unless the program file it runs has its setuid permission bit set. In which case, the kernel then takes the effective uid from the file's owner instead, while the real uid remains inherited as before. A process therefore gets its effective uid in one of two ways: from the process that invoked it, or from the owner of a setuid program file. (Groups work the same way, with a real gid, an effective gid and a setgid bit, beside the supplementary groups, which are inherited unchanged.)

By convention, the gate is the only program of Man-In-Grey that can optionally be given the setuid bit. When the gate is not setuid, it inherits its effective and real uids from the program that invoked it. When it is setuid, it inherits its real uid from the program that invoked it, and it inherits its effective uid from its file owner. Thus, the gate process has reliable information directly from the kernel on who invoked it, as that is its real uid. It also has reliable information directly from the kernel on who owned its executable file, as that becomes its effective uid.

Due to this mechanism the effective uid for a setuid gate program can be different than the effective uid of the program that invoked it. In the chain of events of program A running and then invoking the gate, the effective uid in that thread of execution will start as the effective uid for program A, and then the effective uid will change to match the uid of the gate executable file owner. We can say that the effective uid change from A to B, where A is the invoking programs effective uid, an B is the owner of the gate executable file.

Instruction language

An instruction language is defined by the application developer and is built into the application. He writes it as data, its language definition, , and both sides of the account divide read the same definition. On the A side, the composer writes in the language by calling functions on the journal interface, one function per instruction, made from the definition. On the B side, the guard checks the journal first against the definition, then against what a definition cannot say, the constraints among it.

The instruction language is not specific to Man-In-Grey. An application that mounts home directories has a language of mount and unmount; one that manages accounts has a language for making and deleting them. Each gate starts the guard and the interpreter of one instruction language, and they refuse a journal written in another language. These coherency checks are due to the journal carrying the name of its language and the hash of its definition, and due to syntax checking of the constituent instructions passing.

A language can be made as narrow as its application. The narrower it is, the less a journal can say, and the less the guard has to rule out. The example language, , can name no file at all: what it writes, and where, is partially compiled in, and partially derived from the name of the invoking user account.

Narrow is not the same as primitive. A journal can be guarded only at the level of the work it asks for. An instruction that names the work, such as making a child account, can be checked against who asked and what he is allowed. A language of primitive instructions, such as setting a uid or mounting a path, would leave the guard to work out what request they add up to, and to check every value the composer chose against records it would have to consult again. The instructions of a language are therefore requests, specific to the work to be done.

Journal form

Every journal has the same form, whatever its instruction language: declarations, then the instruction list. The form is Man-In-Grey's own, a generic language; an instruction language is a set of instruction formats written within it, as an instruction set is defined within an assembler's syntax.

Language definition

A language definition is a map of four sections, written by the application developer as a literal value in a module of its own, such as Emplace_Bio·Language.py, beside the module's NAME. It is data, not code. The guard, the interpreter and the journal interface all read the same definition, and the guard's copy is installed with the guard, owned by root, so account A cannot change it.

A list of type declarations, each [<name> ,<type expression>]. A type expression is a primitive, the name of a type declared earlier in the list, or a compound: ["dictionary" ,[<key> ,<type expression>] ...] or ["list" ,<type expression>]. A type can therefore not refer to itself. A list of instruction formats, each [<format name> ,[<direction> ,<type name>] ...]. The direction is in, out or in-out; the type name is a primitive or a declared type. Arguments are given by position, so the format fixes how many an instruction takes. The list of type names a journal's result can have. A map from each operation specifier to its format name. Its keys are the explicit list of the operations a journal can use. The operation specifier is also the name of the Python function that carries the instruction out.

The primitives are text, integer, bytes, boolean and handle. A handle is a value an instruction produces for later instructions, such as an open file. No literal can be a handle, so a journal can name an open file only through the variable the instruction that opened it wrote; no result can hold a handle, since it means nothing outside the interpreter.

In a declaration, a position decides what an element is: the first element of a list is always a type or a name, never data, so no element has to be inspected to find out what it is. A dictionary entry is [<key> ,<type expression>], and an empty dictionary is ["dictionary"].

Types are compared by name. A variable of the type short_name is not a variable of the type text, even when short_name is declared as text, so a variable passes only where the format names its type exactly, and account A cannot make a type of his own. A literal is compared with the structure of its type. The check uses Python's type(), not isinstance, since isinstance(True ,int) is true and a boolean would otherwise pass as an integer.

The smoke test's language uses every part of the form:

DEFINITION = { "list__type": [ ["directory" ,"text"] ,["file_name" ,"text"] ,["mode" ,"text"] ,["account_name" ,"text"] ,["permission" ,"integer"] ,["file" ,"handle"] ,["content" ,"bytes"] ,["summary" ,["dictionary" ,["open_count" ,"integer"] ,["unlink_count" ,"integer"]]] ] ,"list__format": [ ["format__open" ,["in" ,"directory"] ,["in" ,"file_name"] ,["in" ,"mode"] ,["in" ,"account_name"] ,["in" ,"permission"] ,["out" ,"file"]] ,["format__write" ,["in-out" ,"file"] ,["in" ,"content"]] ,["format__unlink" ,["in" ,"directory"] ,["in" ,"file_name"]] ,["format__summary" ,["out" ,"summary"]] ] ,"list__result": ["summary"] ,"map__instruction": { "open": "format__open" ,"write": "format__write" ,"unlink": "format__unlink" ,"summary": "format__summary" } }

open writes the handle of the file it opens to its last argument; write reads and writes its file, as it changes the file; summary writes counts, which a journal can make its result.

A definition has a well-formed check of its own, is__well_formed_language, in Language.py, made when the guard and the interpreter start and when the journal interface is made: every head a known type, every name declared once, every type used declared before, every format named in the operation map declared, and every operation specifier a Python function name not beginning with _. The names declare, result, finish and release are kept by Man-In-Grey and refused as operation specifiers. The definition's hash is the SHA-256 of its canonical CBOR encoding.

Journal

A journal is a CBOR map of seven entries:

The version of the journal's form, now 4. A guard or interpreter refuses a journal of another version. The name of the instruction language the journal is written in, such as Emplace_Bio. A guard and an interpreter refuse a journal in a language other than their own. The hash of the language definition the journal was composed against. A guard refuses a journal whose hash differs from its own definition's, which tells a person whose copy of the definition is out of date why, in place of a puzzling refusal of some instruction. When, on which host and by which account the journal was composed, and the composer that ran. The variables, each [<name> ,<type name>], the type one the language definition declares. The name of the variable whose value is the journal's result, or null for a journal with no result. The instructions, in the order the composer placed them.

Each instruction is a map of two entries: operation, its operation specifier, and list__argument, the list of its arguments, in the order of its format. Each argument is a pair whose first element says how to read the second:

The value itself, whatever it is, a map included. It is never examined to find out what it is. A variable, which the instruction reads, writes, or both, as its format's direction says.

The kind of an argument is carried beside it, never inferred from its value, so no literal can be taken for a variable. The first four instructions of the journal in , decoded, and written in JSON notation:

{"operation": "display_name", "list__argument": [["literal", "Thomas"]]} {"operation": "paragraph", "list__argument": []} {"operation": "text", "list__argument": [["literal", "I write "], ["literal", []]]} {"operation": "text", "list__argument": [["literal", "software"], ["literal", ["emphasis"]]]}

Since arguments are given by position, the well-formed guard requires exactly the number an instruction's format takes: a text instruction carrying a third argument is refused, whatever that argument says. A journal of the Smoke language, in which one instruction writes a variable that later instructions read, with a byte string written as b"...", as JSON has none:

"list__variable": [["unbound_conf", "file"], ["summary", "summary"]] "result": "summary" {"operation": "open", "list__argument": [["literal", "/etc/unbound"], ["literal", "unbound.conf"], ["literal", "replace-keep"], ["literal", "Thomas"], ["literal", 292], ["variable", "unbound_conf"]]} {"operation": "write", "list__argument": [["variable", "unbound_conf"], ["literal", b"server:\n"]]} {"operation": "summary", "list__argument": [["variable", "summary"]]}

The meta entry is a note, not evidence: account A writes the whole journal, and could write anything there, so the guard and the interpreter never base a decision on it.

Variable

A composer writes instructions, but it does not run them. When an instruction produces a value, as for example an instruction that makes an account and produces its uid, the value does not exist yet at the time the composer runs. The composer therefore declares a variable to hold it, and gives the variable to the instruction that writes it and to each instruction that reads it:

account = journal_iface.declare("www" ,"account") journal_iface.make_account("Thomas·www" ,account) journal_iface.add_to_group(account ,"http")

Here make_account's format writes its second argument, and add_to_group's reads its first. The two instructions are of a language an application that manages accounts would define. An instruction can write as many variables as its format has out and in-out arguments, and a variable of a dictionary type holds several values under its keys. A printed journal shows a variable as <name where an instruction reads it, >name where it writes it, and <>name where it does both.

Well-formed

A journal is straight-line: no branch, no loop. So one pass from the first instruction to the last settles, for every argument, whether it is well formed, before anything runs. The well-formed guard makes that pass, is__well_formed_journal in Guard·WellFormed.py, and refuses the journal when:

  • a variable is declared twice, is not a name, or has a type the definition does not declare;
  • an instruction's operation specifier is not in the definition, or it has a number of arguments other than its format's;
  • an argument is not a pair of a known kind;
  • a literal is given where the format writes, has a type that holds a handle, or lacks the structure of its type;
  • a variable is not declared, or its type is not the one the format names;
  • a variable is read, as in or in-out, before any instruction has written it;
  • a variable an instruction writes is given to that instruction a second time;
  • the result is not a declared variable, has a type not among the definition's result types, or is never written.

A variable can be written more than once; what the pass tracks is whether it is defined, and its type, at each point. The journal interface makes the same pass as each declaration and instruction is placed, so a composer's mistake is an error when the composer makes it, and the guard and the interpreter make it again on the journal they receive.

Result

Man-In-Grey is a function interface: account A gives a journal and can be given a value back. A journal that names a result has the value of that variable handed back when it is played. The interpreter writes the result to its descriptor 3 as a CBOR map, {"type": <type name> ,"value": <value>}, then writes its verdict line. The gate reads descriptor 3 as it reads the interpreter's other output, up to 16 MiB, never examines it, and only once it takes the journal as played forwards it unchanged to its own descriptor 3. A journal that is refused, or whose play fails, gives no result.

The invoking program opens descriptor 3 to receive the result. When it leaves descriptor 3 closed, the gate opens /dev/null there, and logs that it discarded the result. Whoever receives a result decodes it and checks it, as the gate cannot: the type name says which of the definition's result types it is.

Program Orchestrator

The orchestrator is a utility program provided with Man-In-Grey. The orchestrator calls a composer program, then sends the resulting journal to a gate program, and prints the result the gate hands back. Like all processes, when the orchestrator program runs, it has a real and effective uid. When the orchestrator is run from a shell, these are both inherited from the shell, and are typically pointing to the login user. In any case, the composer that it invokes will then run with the same effective and real uids as the orchestrator. When the gate executable file has its setuid bit set, when the gate is invoke by the orchestrator, the gate will inherit its real uid from the orchestrator, and will take its effective uid from the gate's executable file owner.

The orchestrator is given a composer file. It runs the file, and calls one function in it, compose(prov ,journal_iface). The file can define other functions as helpers of it, but the orchestrator calls none of them. Running several composers into one journal would need a way for each to keep variables of its own and to share others, which this version does not have; see .

An application making use of Man-In-Grey can bypass the orchestrator and call the composers and gate on its own. When this happens the gate's real ID will be that of the application. For a setuid gate, its effective uid still comes from its file owner. Such an application makes a Journal·Interface.JournalComposed and its Journal·Interface.JournalInterface from the definition, places instructions however it likes, and calls Man_In_Grey.admit(gate ,journal_bytes), the orchestrator's work function, which invokes the gate with descriptor 3 open and returns the gate's exit status and the result.

It is possible that the application is designed such that the executable file for the gate does not have its setuid bit set; or that it does have its setuid set, but the gate owner is the same as that of the orchestrator or that of the direct calling application. In such a case, the execution thread will keep the same real and effective uids the entire time it runs. In this mode the Man-In-Grey can not achieve anything the application could not have achieved on its own, but it still might be a convenient expression of the desired functionality. For example, as an alternative to template filling without effective uid changes.

Gate

The gate is compiled because Linux ignores the setuid bit on a script started with #!. Given no arguments, the gate prints its usage. Its command flags reports the gate's real and effective uid and gid with their names, whether they differ, the name of the gate's instruction language, and the paths of the guard and the interpreter.

> /usr/local/lib/Man-In-Grey/Man_In_Grey__Gate/Man_In_Grey__Gate·Emplace_Bio flags real.uid=2006 real.user-name=Thomas real.gid=2006 real.group-name=Thomas effective.uid=996 effective.user-name=http effective.gid=995 effective.group-name=http uid-differ=1 gid-differ=1 language=Emplace_Bio guard.path=/usr/local/lib/Man-In-Grey/Man_In_Grey/Emplace_Bio·Guard.py interpreter.path=/usr/local/lib/Man-In-Grey/Man_In_Grey/Emplace_Bio·Interpreter.py

Here Thomas asks the example language's gate, , installed setuid to the web server's account http: the real ids are his, and the effective ids are http's.

Th admit command takes the journal on standard input. There is an option check-only that will print check messages without doing anything. Without this option, when the gate is asked to admit a journal, it:

  1. puts every signal's disposition back to its default, turns off the interval timers, and clears the blocked mask, so no signal state the invoking program left can act later;
  2. opens /dev/null on any of descriptors 0, 1 and 2 the invoking program left closed; keeps descriptor 3, the result descriptor, when the invoking program left it open, marked so that neither the guard nor the interpreter inherits it, and opens /dev/null there when it did not; and closes every descriptor above 3, so nothing the invoking program opened reaches the guard or the interpreter;
  3. raises each resource limit that could stop the guard or the interpreter partway, file size and CPU time to unlimited, address space and data size to 1 GiB, stack size to 8 MiB, and open files to 64, as far as the hard limit allows, or past it when account B is root; and refuses when one stays too low;
  4. finds the guard and the interpreter at paths fixed when the gate is compiled, relative to the gate itself, so account A cannot name others;
  5. refuses unless the guard and the interpreter, and every directory above them, are owned by root or by account B, and writable by no other account;
  6. clears the environment, setting only PATH and LANG, sets the file mode mask to 077, marks the process not dumpable, and changes directory to /;
  7. records its real ids, account A's, in MIG__REAL_UID, MIG__REAL_GID and MIG__REAL_USER_NAME, for the guard and the interpreter;
  8. reads the journal from its standard input, up to 16 MiB;
  9. when accounts A and B differ, makes its real uid account B's, so the kernel refuses account A's signals, and ignores the signals a terminal sends; see ;
  10. starts /usr/bin/python3 -E -s -B on the guard, with the journal on its standard input, and goes on only when the guard approves the journal;
  11. starts the interpreter the same way, with the same journal and a pipe to the gate on its descriptor 3, and takes the journal as played only when the interpreter writes its verdict line and exits 0;
  12. forwards what the interpreter wrote on its descriptor 3, the result, to the gate's own descriptor 3; see .

The guard and the interpreter, before they import anything, each check that every module they load, the guard program among them, is owned by root or by account B, and writable by no other account. A module runs code when it is imported, so the check comes first.

The constraints, not the gate, decide which accounts can give a journal. The gate decides only whether the guard and the interpreter it would start can be trusted, and whether the guard approved the journal.

One gate per instruction language

Man-In-Grey's general gate is the library module Gate.lib.c, whose function Man_In_Grey__Gate·Gate·run takes the name of the instruction language, the guard's path and the interpreter's path, and the command line. An instruction language's gate is a *.CLI.c of three lines that calls it with the three fixed. The gate of the example language:

#include "Gate.lib.c" int main(int argc ,char **argv){ return Man_In_Grey__Gate·Gate·run("Emplace_Bio" ,"../Man_In_Grey/Emplace_Bio·Guard.py" ,"../Man_In_Grey/Emplace_Bio·Interpreter.py" ,argc ,argv); }

The general gate is curried, with its first three arguments supplied when the gate is compiled. Whoever invokes a gate can choose neither program it runs; if he could, he could give it a guard that approves everything. The language name holds no space and no control character, and the gate refuses to run when it does.

Output rule

Every line the guard and the interpreter write is copied to the person, marked guard: or interpreter:, and to the system log under the name Man_In_Grey__Gate, beside the gate's own lines, marked gate:. The gate logs each journal's course itself, whatever the guard and the interpreter write: received, with account A, account B and the journal's size; isolated, when the gate gives up account A; then approved or refused; then interpreting; then interpreted or failed; and, for a journal with a result, result-forwarded, result-discarded when descriptor 3 was not open, or result-lost when it could not be written. A line breaks the gate's rules when it is not UTF-8, or holds a control character (C0, DEL or C1), or is longer than 4096 bytes, or is one line more than 2000; the gate then stops the program and refuses the journal. Unicode is otherwise welcome. The guard writes any control character it quotes as \u{XXXX}, and the example language's language check refuses any text that holds one.

Transport

A journal reaches its interpreter by starting the interpreter's gate with the journal on standard input. Since a journal is data, it could travel other ways, such as over a Unix domain socket to an interpreter already running, which would learn account A through SO_PEERCRED. Man-In-Grey does not do this. It is the mechanism a program that receives requests is built with, not such a program itself.

Guard

Accounts exist to limit what programs can do. The guard decides, before anything runs with the effective uid of account B, whether the work account A asks for is allowed: it reviews the journal and checks it against a set of constraints, and approves the journal only when every constraint is met.

The kernel tells the gate which account invoked it, as the real uid, and the gate passes it on, so the guard knows it also. The kernel does not say which program invoked the gate. As the guard invocation is compiled into the gate, the guard can know the provenance of the journal from the point it was given to the gate, but not before that.

Two checks are needed by nearly every guard, whatever its instruction language. The first is that the journal is well formed: that it decodes, and agrees with the language definition in every declaration and argument. Man-In-Grey makes this check itself, the well-formed guard, , from the definition, so a language writes no code for it. The second is who account A is. The gate had account A's uid from the kernel, as its real uid, and records it for the guard before giving it up, ; the real gid and supplementary groups the gate inherited from the invoking program stay account A's, and the guard reads them from the kernel. Account A cannot misstate any of them. A guard can therefore allow a journal from the accounts it names, or from the members of a group, as its constraints decide.

The other checks a guard makes belong to its instruction language: what a definition cannot say, such as an order the instructions are to come in or the values a literal can take, and the constraints. A language gives them as LIST__CHECK, in its guard check module, such as Emplace_Bio·GuardCheck.py, a list of named checks in the order they are made, each given the instructions as the well-formed guard has resolved them, its literals' values and, for each variable, the instruction that last wrote it. The example language's four checks are in .

Constraint predicate

A guard's constraints are code. The guard is a Python program, written for one application, so its constraints are Python functions written at the top of the guard itself, where they go with it, and no language for expressing constraints is needed. Each is a constraint predicate, named in the manner of is__allowed_account(user_name) or is__allowed_open(directory ,name ,mode ,owner ,permission), and the guard refuses a journal when one does not answer True. A predicate can compare with a list, ask whether an account is in a group, or anything else Python can say. The predicates sit between the lines # constraints begin and # constraints end, so that install-gate can put in an administrator's and keep them when the guard is installed again. As promoted with Man-In-Grey, they refuse every account.

Some constraints recur from one guard to the next, and the library module Guard·LibraryConstraint.py holds them, for a guard's predicates to call:

The account is in the group by the group database: listed as a member in /etc/group, or having it as its primary group. The gate's real gid or supplementary groups include the group. These are what the invoking program held, passed on by the kernel, so an account that joined the group after its session began does not have it yet, though is__group_member already says yes. The path is the directory or lies within it, both absolute and in normal form. The permission sets no bit the limit does not: 0o600 is within 0o644, and 0o4755, setuid, is within neither 0o644 nor 0o755.

The guard checks and imports its modules, Guard·LibraryConstraint.py among them, only after its predicates are defined, and calls the predicates only after that, so a predicate can call Guard·LibraryConstraint.is__group_member by name, though the import comes later in the file. Code at the top level of the constraints runs before the ownership check, so the constraints hold only definitions, and imports of the standard library at most. The interpreter imports the guard program, for what execution needs from its constraints.

Verdict

A guard reads the journal on its standard input. Its standard error is for the person: one line per finding, as <tag>: <message>, the first two name: and version:, then such lines as check-passed: wellformed or constraint-broken: <what is wrong>. Its standard output is for the verdict alone. A guard approves a journal by writing exactly one line there, guard <language> check passed, with the language name the gate has compiled in, and exiting 0. The gate takes the journal as approved on that line and that status together, and on nothing else, and only then admits it to the interpreter; a guard that refuses exits 1, and one that cannot check exits 2.

The verdict travels out of band from the findings. A finding quotes the journal, a file name for instance, and goes to standard error, so nothing in a journal can put a line on standard output. A crash cannot approve a journal either: an uncaught Python exception exits 1, and a guard that dies leaves no verdict.

Interpreter

The gate starts the interpreter only after the guard has approved the journal, with the effective uid of account B and the same journal on its standard input. Generally the interpreter does not check the constraints as that is the guard's work, but some checks will naturally occur as part of interpretation. Where useful the guard program module can be included so as to pull in the helper functions.

The gate logs when a journal is received, approved, and interpreted. The interpreter writes to standard error, as <tag>: <message>, the highlights of what it does, as its developer chooses them. Its standard output is for its verdict alone, as the guard's is: when it has played the whole journal, it writes the result to descriptor 3, when the journal names one, then exactly one line on standard output, interpreter <language> journal played, and exits 0. The gate takes the journal as played on that line and that status together; an interpreter that exits 0 without it, having returned early or not being the program it should be, is logged as failed. Otherwise its exit status is 1 when it stopped partway, and 2 when the journal could not be read or is not well formed.

A language gives the implementation of its instructions as a class, LibraryInstruction, in its instruction library, such as Emplace_Bio·LibraryInstruction.py. An instance is made once for each journal, and holds what the instructions build up between them. For each operation specifier in the definition it has a function of that name. The interpreter finds the functions by the names the definition lists, never by a name taken from the journal, so no other function of the class, nor anything the module imports, can be reached from a journal. It gives each function the instruction's arguments by position:

A copy of the value, so that the function cannot change a variable through it. An empty list, a box, to which the function appends the value. A box holding a copy of the variable's value, which the function replaces.

After each call, every box is to hold exactly one value, of its format's type; the interpreter takes the value out and keeps it as the variable's. An empty box is evidence that the function wrote nothing, which no stand-in value could be. A function reports failure by raising an exception. LibraryInstruction can also have finish(), called after the last instruction, and release(), called at the end whatever happened.

The verdict line says only that the interpreter reached its end. It cannot undo what an interpreter did before failing, and it is the interpreter's own claim, not evidence that what it did was right.

Execution stops at the first error. What the interpreter did before then stays done, except what its instruction language undoes; for the example language, see . Playing a journal as a transaction is a possible future feature; see .

Isolation from account A

The aim is that a journal be played as a transaction: either all of it takes effect, or none of it does, with nothing in between. Man-In-Grey is not there yet, since an interpreter can still fail partway, as discusses. But no interpreter can be transactional while account A can stop it partway, and until this design, account A could: by sending a signal to the gate, the guard or the interpreter, or by having arranged before the gate started for a signal to arrive later. This chapter explains signals, the uid that lets a setuid program give up account A, and what the gate does so that once it has the journal, account A can no longer interrupt it.

Signal

A signal is a small message the kernel delivers to a process: a number, such as SIGTERM, asking it to end, SIGINT, sent by Ctrl-C, or SIGKILL. One process sends a signal to another with the system call kill; the kernel also sends signals of its own, as when a timer expires or a process writes to a pipe nobody reads.

Sending a signal is two steps. First the kernel decides whether the sender may signal the target at all: a process may signal another when the sender's real or effective uid equals the target's real uid or its saved uid, described below, or when the sender is root. If neither holds, kill fails with EPERM, "Operation not permitted", and no signal exists. Only then, second, is the signal delivered, and the target's disposition for that signal decides what happens: the default action, which for most signals ends the process; ignoring it; or running a handler the program installed. Two signals, SIGKILL and SIGSTOP, can be neither handled nor ignored, so a handler can never protect a process from them. Only the first step can.

A setuid gate starts with account A as its real uid, so it passes the first step for account A. Account A could therefore end the gate, the guard or the interpreter with SIGKILL at any moment, the interpreter halfway through a journal included.

Saved uid

A process holds three uids, not two: real, effective, and saved. When a setuid program is executed, the kernel sets the effective uid to the file's owner and copies it into the saved uid; the real uid stays as inherited. A setuid gate owned by account B therefore starts holding account A as its real uid, and account B as its effective and saved uids.

A process may rearrange its uids among the ones it already holds, without privilege, but it cannot take a uid it does not hold. The call setreuid(real ,effective) may set the real uid to the current real or effective uid, and when it changes the real uid it sets the saved uid to the new effective uid. So a setuid gate may call setreuid(B ,B), making all three of its uids account B's. It gains nothing by this, since it already acts with account B's rights; it only gives up its connection to account A, and once given up, account A cannot be taken back. Only a process with CAP_SETUID, in practice root, may set a uid it does not hold, which is how login starts a shell under the account a person signed in to.

The saved uid exists so that a setuid program can drop its rights for a while and take them back: it sets its effective uid to its real uid, does some work on the person's behalf, and returns to the saved uid. Man-In-Grey uses the same rules the other way, to drop account A for good.

Isolating the gate

Once the gate has read the whole journal, and before it starts the guard, it makes its real uid account B's, as above. From then on account A matches neither the gate's real uid nor its saved uid, and the kernel refuses account A's signals at the first step, SIGKILL and SIGSTOP included. The guard and the interpreter are started after this, and inherit all three uids. The gate logs the moment:

gate: received: real uid 2006 (Thomas), effective uid 996 (http), journal of 1857 bytes gate: isolated: real uid now 996 (http); account A can no longer signal the gate

Here is account A trying, after that line, to stop the example language's gate, installed setuid to http. The guard was slowed for the demonstration so there was time to try:

gate pid 693 Uid: 996 996 996 996 kill: (693) - Operation not permitted kill: (693) - Operation not permitted kill: (693) - Operation not permitted

The Uid line from /proc/693/status gives the real, effective, saved and file-system uids, all http's; the three refusals are SIGKILL, SIGSTOP and SIGTERM. The run went on to place the page.

Waiting until the journal is read costs nothing. Until then the gate has done nothing that would need undoing, so account A interrupting it earlier only stops a run that has not begun.

Signal state that outlives exec

Refusing account A's signals is not enough by itself, since account A could arrange beforehand for a signal to arrive after the switch. Three pieces of a process's signal state survive exec, so the program that invokes the gate can leave them behind:

A timer set with alarm or setitimer keeps running in the gate. When it expires, the kernel sends SIGALRM, SIGVTALRM or SIGPROF to the gate itself, with no question of who set the timer, so the switch does not stop it. Each ends the process by default: a timer set to expire partway through would end the interpreter there. The invoking program can block a signal and send it, so it waits, pending. Both survive exec, and the signal would be delivered whenever it came to be unblocked. A signal set to be ignored stays ignored. Ignoring SIGCHLD, for one, makes the kernel discard a child's exit status, so the gate could not learn how the guard ended.

The gate therefore settles its signal state first, before anything else, as it settles its descriptors and resource limits: it puts every signal's disposition back to its default, turns off the three interval timers, and clears the blocked mask. Clearing the mask delivers any signal already pending, then and there, while the gate has done nothing. A process that goes past its limit of CPU time or of file size is sent SIGXCPU or SIGXFSZ; the gate raises those limits at its start, and refuses to run when it cannot.

The test tester/authored/Emplace-Bio starts the gate from a process that leaves each kind behind: a timer set to send SIGALRM fifty milliseconds in, an ignored SIGCHLD, and a blocked, pending SIGTERM. With the gate settling its signals, the first two runs place the page, and the third ends at once, having changed nothing. With the settling step taken out, the timer ends the gate partway, the ignored SIGCHLD makes it refuse, and the pending SIGTERM stays blocked, unnoticed.

The terminal

A terminal sends signals of its own to the programs running in its foreground: SIGINT for Ctrl-C, SIGQUIT for Ctrl-\, SIGTSTP for Ctrl-Z, SIGTTIN and SIGTTOU when a program in the background reads it or, if the terminal is so set, writes it, and SIGHUP when it is closed. These come from the terminal driver, not from a process, and are not checked against uids. So when it isolates itself, the gate also ignores all six; the guard and the interpreter inherit that. No key on a terminal sends SIGKILL or SIGSTOP.

Pressing Ctrl-C, Ctrl-\ and Ctrl-Z during a run of the example ended the orchestrator, account A's own program, by SIGQUIT; the gate, the guard and the interpreter went on, and the page was placed. The gate also ignores SIGPIPE, so a reader of its output that has gone away does not end it; its lines still reach the system log.

One signal still reaches the gate from account A: the kernel lets any process in the same session send SIGCONT, whatever its uid. SIGCONT only resumes a stopped process, and account A can no longer stop the gate, so it does nothing.

Who account A is, afterwards

Once the gate has given up account A, the kernel no longer says who account A is: the guard and the interpreter find account B as their real uid. The gate records account A before giving it up, in MIG__REAL_UID, MIG__REAL_GID and MIG__REAL_USER_NAME, having first cleared the environment, so the variables say what the gate says and nothing account A put there. The guard and the interpreter read account A from them, and refuse to work when the uid and the user name do not name the same account. Knowledge of account A therefore rests on the gate, which had it from the kernel.

The gate gives up only the uid. Its real gid and supplementary groups stay account A's, so Guard·LibraryConstraint.has__real_group still answers for account A's groups.

What isolation does not give
  • Before the journal is read, account A can still stop the gate. Nothing has been done, so nothing is lost.
  • When accounts A and B are the same, there is nothing to isolate, and the gate does not; the person can interrupt his own run, which has no more than his own rights.
  • Root can signal any process. Root is trusted.
  • The interpreter can still fail partway on its own. Isolation removes account A as a cause, which a transactional play needs, but does not make the play transactional; see .

Writing a composer

A composer is a Python file defining compose(prov ,journal_iface), kept in a directory of its author's choosing, named composer in the examples here. What a composer does is said by the instructions it places.

A composer runs with the orchestrator's uids, which are normally account A's, and so with account A's rights. If another account could change a composer, that account's code would run with account A's rights, and its instructions would reach the gate in account A's name. The composer, and every directory from / down to it, is therefore to be owned by account A or by root, and writable by no other account.

This ownership protects account A, not account B, and the gate cannot enforce it. The gate is given a journal, never the program that made it, and anything it is told about the composers comes from account A. To the gate and the guard, every journal is account A's, whatever made it. Composer ownership is therefore a convention, kept by whoever installs an application's composers. Man-In-Grey's orchestrator keeps it for its own runs: before running the composer it makes the check, and it refuses a composer that is a symbolic link. An application that acts as its own orchestrator keeps the convention itself. To run a composer someone else wrote, review it and copy it into a directory of your own.

# composer/bio.py def compose(prov ,journal_iface): journal_iface.display_name("Thomas") journal_iface.paragraph() journal_iface.text("I write software." ,[])

This composer writes in the example language; shows a whole one. compose is given prov, which says where the composer is:

The composer's own file name less .py, for a composer named for the file it writes. The name of account A. The composer's absolute path, the directory holding it, and the working directory of the run.

Man-In-Grey orchestrate <composer> runs the composer. No option given to Man-In-Grey reaches compose; a composer's settings are written in the composer itself. The journal_iface a composer is given is that of the gate's instruction language: the orchestrator asks the gate for its flags, loads the definition named for its language, Emplace_Bio·Language.py for Emplace_Bio, and makes the journal interface from it. It has one function for each operation specifier, given the instruction's arguments in the order of its format, and two more:

Place an instruction. An argument that is a variable declare returned is given as that variable; any other value is a literal. Declare a variable, and return it. Make the variable the journal's result.

Each call is checked as it is made, by the pass the well-formed guard makes, so a mistake raises JournalError in the composer, naming the instruction and argument, and no journal reaches the gate. A composer of the Smoke language, which opens a file, writes it, and makes a summary its result:

A run that changes files is best preceded by two that do not. The first shows the journal while nothing has left the person's account; the second has the guard check the journal, and the gate stop before the interpreter:

Man-In-Grey orchestrate composer/bio.py gate <gate> print compose-only Man-In-Grey orchestrate composer/bio.py gate <gate> check-only Man-In-Grey orchestrate composer/bio.py gate <gate> Run the composer, a file, and invoke the gate with the journal. The gate to invoke, which also sets the instruction language the composer writes in. Required: the orchestrator has no gate of its own. Print the journal after composing. Stop after composing; nothing reaches the gate. Have the gate run the guard and not the interpreter.

The command and its path come first, then the gate, and the options follow, as plain words; given no arguments, Man-In-Grey prints its help, and so does the gate. A journal with a result has it printed as one line, result: <type name> <value>. The exit status is 0 when the run did what it was asked; 1 when the guard refused the journal or an instruction failed to execute; and 2 when the run could not start, the composer failed or was refused, or the gate, guard or interpreter could not run or broke the gate's rules. The guard's and interpreter's lines are also in the system log; on a system with journald, journalctl -t Man-In-Grey_gate shows them.

Installing a setuid gate

A setuid gate and everything its guard and interpreter load are to be owned by root or by account B, in directories no other account can write, and the gate, the guard and the interpreter check this on every run. A Harmony consumer/ directory is owned by the person who promoted into it, so a setuid gate there refuses to run, and so does root running the gate there. Installing an instruction language's gate, guard and interpreter is therefore a step of its own, done with root's rights by the Man-In-Grey administrator, the person who installs Man-In-Grey and the applications that use it.

The installation is done by install-gate, which is promoted beside Man-In-Grey and is run by root. The administrator runs it through Man-In-Grey:

consumer/Man_In_Grey/Man-In-Grey install <gate> owner <account> [group <group>] into <directory> [constraints <file>]

Run by root, Man-In-Grey install runs install-gate directly. Run by any other account, such as a developer account without sudo, it runs it through su, which asks for root's password; it first makes a constraints file's path absolute, as root's shell starts in another directory. Root can also run install-gate install itself, with the same arguments. Either way the administrator runs, with root's rights, the install-gate and the files of the tree he names, so he is to install only a tree he has reviewed.

It copies Man_In_Grey/ and the one gate named from Man_In_Grey__Gate/ into the directory, side by side, as the gate's compiled paths expect. Every file and directory it installs is owned by root and writable by no other account, except the gate, which it gives to account B, the owner account named, and to a group, and then makes setuid and setgid. The order matters, since changing a file's owner clears its setuid and setgid bits. The gate's mode is 6755: the mode 755 with the setuid bit, 4000, and the setgid bit, 2000, added. The setgid bit gives the gate the group as its effective gid, and an interpreter makes its files with the effective gid's group: only root can give a file away, so an interpreter whose effective uid is that of an account B other than root makes files that account B owns, in that group. The group is account B's own unless group <group> names another, such as a group the web server reads through. When account B and the group are both root's, the setgid bit changes nothing, and the mode is 4755.

With constraints <file>, a Python file of predicates, install-gate puts them between the constraint marks of the gate's guard. Without it, the constraints of a guard already installed are kept, so installing again brings a new guard and keeps the administrator's constraints; a first installation gets the guard's as promoted, which refuse every account. The constraints of every other installed guard are kept too. install-gate refuses a directory that is not absolute, that an account other than root owns or can write, or that is on a file system mounted nosuid, where the kernel ignores the setuid and setgid bits, as it does on removable drives and some separately mounted /home directories. It ends by printing the installed gate's flags, as root sees them: real uid and gid root's, effective uid account B's, effective gid the group's. Promotion replaces files and sets neither the owner nor the setuid bit, so the installation is redone after each promotion that changes the gate, the guard or the interpreter. The installation is a candidate for Man-In-Grey itself, once there is a language for installing programs.

Example: Emplace-Bio

A host publishes a bio page for each of the accounts it allows, at /srv/http/bio/<user_name>.html, with the account's picture beside it. The directory belongs to the web server's account, http on Arch and www-data on Debian, so a person cannot write his page there himself. He writes a composer giving his display name, his text and his picture, and runs Man-In-Grey with the gate Man_In_Grey__Gate·Emplace_Bio, which the administrator has installed setuid to the web server's account. The interpreter then runs with the effective uid of http, and builds the page.

Here account B is not root, and the gate stands between two ordinary accounts. The example is made so that a reader can see each step is safe: a person can change only his own page, and only to a page made of his text and picture.

The instruction language The page's title and heading. Given once. Starts a paragraph. A run of text in the current paragraph. list__style is a list drawn from strong, emphasis, underline and strikethrough; an empty list is plain text. The bytes of a PNG or JPEG image. At most once.

Its definition, in Emplace_Bio·Language.py:

DEFINITION = { "list__type": [ ["name_text" ,"text"] ,["run_text" ,"text"] ,["list__style" ,["list" ,"text"]] ,["image" ,"bytes"] ] ,"list__format": [ ["format_name" ,["in" ,"name_text"]] ,["format__empty"] ,["format__run" ,["in" ,"run_text"] ,["in" ,"list__style"]] ,["format__image" ,["in" ,"image"]] ] ,"list__result": [] ,"map__instruction": { "display_name": "format_name" ,"paragraph": "format__empty" ,"text": "format__run" ,"picture": "format__image" } }

No instruction writes a variable, so every argument of a journal in this language is a literal, and the journal has no result.

No instruction names a file. The page's file names come from the user name of the real uid, which the kernel gives the guard and the interpreter, so a person can write only his own page. The directory comes from page_directory() among the guard's constraints, which the administrator writes. A journal describes the whole page: a run that gives no picture removes the picture an earlier run placed.

Decoration travels out of band. A run's styles are a list beside its text, not marks in it, and the interpreter turns each style into one fixed tag with no attribute: <strong>, <em>, <u> and <s>, nested in that order. It writes the rest of the page from a fixed form, and escapes every text it is given, so nothing a person gives becomes markup. There is nothing to sanitize: an attribute such as onload, or a <script> element, cannot be expressed in the language.

The filesystem check asks whether the effective uid can write the directory. Python's os.access, like the system call access under it, answers for the real uid unless asked with effective_ids=True, since it was made for setuid programs to ask what the person who ran them could do.

The interpreter

The language's LibraryInstruction builds the page up, one instruction at a time, and its finish() writes the picture and the page to temporary files in the directory, gives each permission 0644, and renames each into place, then removes a picture the page no longer shows. The files are owned by http, the effective uid that made them. The page Thomas's composer gives:

The interpreter's own form is built the way a composer builds a file: constant strings with the escaped texts between them. The Content-Security-Policy line tells the browser to run no script and load nothing but images from the same site, a second wall behind the first, since the page cannot hold script anyway.

Why it is safe
  • A journal names no file, and the well-formed guard refuses an instruction with any argument its format does not have, so a journal cannot point the interpreter anywhere. The page's name comes from account A's user name, which the gate had from the kernel as its real uid, and its directory from the administrator's constraints.
  • Once it has the journal, the gate gives up account A, so Thomas cannot stop the guard or the interpreter partway, and a page is never left half placed by him.
  • The interpreter runs with the effective uid of http, not root, so even a fault in it reaches only what the web server's account can write.
  • The page's text cannot become markup, since the interpreter escapes it and writes every tag itself. The page cannot become server code either: its name always ends in .html, never .php or .htaccess.
  • The guard refuses a page or picture that has been made a symbolic link, and a directory reached through one, so a link cannot redirect the write to another file of http's.
  • The picture is published as given. The content check confirms its format, not what it shows, nor what its metadata says: a JPEG from a phone can carry the place it was taken. A composer that is to strip such metadata does so before placing the picture.
 Known issue The gate checks the guard's verdict, not the guard's work: a guard that writes its approval line without reading the journal approves everything. The guard is installed code the application developer writes, and is to be tested as such. When an interpreter crashes, fails, or breaks the gate's output rules partway through a journal, what it did before then stays done, and the gate can only log the failure. Playing a journal as a transaction is on the road map. The gate writes the result to descriptor 3 after the interpreter has finished, and waits while the invoking program's end of it is full. A program that opens descriptor 3 and never reads it leaves the gate waiting, and once the gate has isolated itself, account A cannot end it; root can. The journal has been played by then, so the wait delays only the gate's exit. A deadline, , would bound it. The gate learns only how the interpreter ended, and what it wrote. Its verdict line says it reached its end; whether the files it made are what the journal meant is the interpreter's own claim, so the interpreter, like the guard, is installed code the application developer writes, and is to be tested as such. Road map
  1. Gates holding only the capabilities their instruction language needs, in place of setuid root.
  2. A language for installing programs, so that installing a gate, guard and interpreter is itself done through Man-In-Grey.
  3. Transactional play: a journal takes effect wholly or not at all; see .
  4. Later, interpreters in a compiled language in place of Python.
 Possible future feature Least privilege

A setuid gate owned by root gives the interpreter every one of root's rights. Root's rights are a set of about forty separate capabilities, among them CAP_DAC_OVERRIDE, to ignore file permissions; CAP_CHOWN, to change owners; CAP_SYS_ADMIN, to mount; and CAP_SETUID, to become another uid. The design is to give each such gate only the capabilities its instruction language needs.

setcap stores chosen capabilities in a program file's extended attributes. A process running that file holds them while its real and effective uid stay account A's. Capabilities are normally lost when a program execs one whose file holds none, as the gate does when it starts Python; the gate keeps them by raising them as ambient capabilities first, which survive the exec. A gate for a language that places files owned by other accounts would then be able to write files and change owners, and nothing else. The gain is uneven: CAP_SYS_ADMIN, needed for mounting, is nearly root by itself.

Deadline

Once the gate has isolated itself, account A cannot signal it, which is the point of isolation. A guard or interpreter that hangs therefore holds the gate, and the request with it, until root ends it. Waiting for a lock is not the case to fear, since a language's code can bound its own waits; SQLite's busy_timeout, for instance, turns a long wait for a database lock into an error. The case is a call that blocks in the kernel, such as a mount on a device that does not answer, or a loop. The resource limit on CPU time does not catch it, since a process blocked in the kernel uses no CPU.

The gate already waits on its children's pipes, so a deadline is a timeout on that wait: when it passes, the gate kills the child and reports the journal failed, as it does for a child that breaks its rules. The deadline is to be compiled into the gate, as the guard's path is, or set by the constraints, never by account A: a short deadline chosen by account A would let it stop an interpreter partway, which isolation exists to prevent. An interpreter stopped by the deadline leaves its work partly done, as one that crashes does, which is what transactional play, , would remedy.

Field of a variable

An instruction can write a variable of a dictionary type, holding several values under its keys, but a later instruction can read only a whole variable. An argument that reads one field, ["variable" ,<name> ,<key> ...], the keys a path into the value, would let an instruction take, say, the uid of an account another instruction made. The path is a list, never a dotted string, since a dotted string would have to be scanned for its dots, and names hold dots. The well-formed guard would check the path against the variable's type as it checks the variable now.

Variables shared between composers

A journal is made by one composer in this version. The first version ran a directory of composers into one journal, each composer standing for one configuration file; with variables, several composers into one journal would each need variables of their own, and some variables shared with others. That is a scoping layer, declarations describing which variables pass between which composers. Its simplest form keeps every composer's variables private to it, scoped by the composer's path, with no sharing, and allows a result only in a journal of one composer.

Interface between arguments and functions

The interpreter calls a language's function with copies of its inputs and boxes for its outputs, and checks what the boxes hold after the call. That is the whole of the interface between a journal's arguments and the code that carries an instruction out. A function interface type, declared with the formats, could give that interface a form of its own: how each argument is passed, what the function returns, how it reports failure. The questions it is to answer are not yet settled.

Session over a pair of gates

A gate is a function call: the invoking program waits, and the kernel ties the result to the call, since it arrives on the descriptor of the gate the program started. Some work finishes after the request, or is between parties that do not share a process lifetime, such as a request against storage not yet attached, or a request to an authority on another machine. For that, two gates, one in each direction, can carry a dialog: the request carries a transaction identifier, and the response carries it back to be recognized.

What the two gates lack is a session, the state common to the request and its response. A synchronous call keeps it in the variables still in scope when the call returns; a dialog has to keep it in the requesting party's own records, as an outstanding request under its identifier. Sending the state with the request, to be sent back with the response, is not a sound trust model, since the responder could alter it. Built on the function call as its base:

  • the requesting party records each outstanding request, and a response is checked against that record, so the responder can complete only the requests that were made, in the shape that was expected;
  • the identifier is random, so the responder cannot answer a request it never received, and one-shot, deleted at the first response, so a replayed response finds nothing to answer;
  • a response that never comes needs a time-out, which needs a clock: deadlines checked only when a journal arrives fire only while there is traffic;
  • a gate into each person's account would be a setuid program for each account; the cheaper forms are delivery by root, or a responder's outbox the requesting account reads.

No identifier makes a responder more trustworthy than it is. Swapping two responses is a lie about which request each answers, and the defense against a lie is checking the answer against the request and against facts the responder cannot forge.

Group and setgid

The gate gives up account A's uid when it isolates itself, , but not account A's real gid or supplementary groups. Signals are permitted by uid alone, so the groups do not let account A interrupt it, and keeping them lets a constraint ask about account A's groups with Guard·LibraryConstraint.has__real_group. Three pieces of work remain:

  • Recording account A's groups. If the gate gave up account A's gids too, with setregid and setgroups, so that nothing of account A's identity remained in the process, it would record the groups first, as it records the uid, and has__real_group would read them from the record.
  • A constraint by group. Guard·LibraryConstraint.is__group_member and has__real_group let a guard admit the members of a group, but the example's guard admits accounts by name; a group, such as bio, is the more natural grant on a real host, and the example could show it.
  • Which group the interpreter's files take. A setgid gate makes its files in the group install-gate gives it. A language that places files for several groups would need the interpreter to set each file's group, which an account B other than root can do only to the groups account B belongs to.
 Checking at the moment of acting

The guard checks the files a journal will touch before the interpreter runs, so they can change in between. Changing them takes write access to their directory, and an account with that access could change them without the gate, so the gap gives no account anything it did not already have. It would still be better closed, so that what was checked is what is acted on.

File locks are the obvious tool, but on Linux they bind only programs that take them: flock and fcntl locks are advisory, and the kernel dropped mandatory locking in version 5.15. The way to close the gap is for the interpreter to make the filesystem checks itself, on the very directory descriptors it then writes through, as the example language's interpreter already does in part by opening its directory without following a symbolic link and renaming into place within it.

Transactional play on Btrfs

Execution now stops at the first error, and what the interpreter did before then stays done, except what its instruction language undoes. A journal would better be played as a transaction: either every instruction takes effect, or none does. Btrfs gives a way to do this for every instruction language, without each language undoing its own work.

A Btrfs subvolume is a directory tree that can be snapshotted. Making a snapshot takes about as long as making a directory, whatever the size of the tree, because the snapshot shares every block with its source; a block is copied only when one side writes it. Before playing a journal, the interpreter would snapshot each subvolume the journal writes in. When the play succeeds, it deletes the snapshots. When the play fails, it puts back each file it changed from the snapshot, then deletes the snapshots. It knows which files those are, since it touched them.

Putting back files one at a time is the general case. A running system cannot replace the subvolume it runs from, such as the one holding /etc, so there the rollback is a restore of each changed file, each in one step, by the same rename the example language uses to put a file in place. Where the destination is a subvolume of its own that is not mounted separately and that no program depends on keeping open, such as a web server's page directory, the interpreter could instead play the journal into a snapshot and then exchange the snapshot and the subvolume in one call, renameat2 with RENAME_EXCHANGE, so the whole change appears at once or not at all. Whether Btrfs allows that exchange between subvolumes is to be confirmed before the design relies on it.

The cost is privilege. Making a snapshot needs ownership of the subvolume, or root, and write access to the directory the snapshot goes in. Deleting one needs CAP_SYS_ADMIN, unless the file system is mounted with user_subvol_rm_allowed. A gate whose account B is not root would need the second, and a gate holding only the capabilities its language needs would need the first, which is nearly root by itself. On other file systems the play stays as it is, and a language undoes its own work where it can, as the example language does by writing its files to temporary names and renaming each into place.

 Change from the first version

The first version had configuration programs calling a planner, a plan, a fixed set of operations, copy, displace and delete, an inner executor, and one gate, man_in_grey_apply, that accepted --inner <file> from its caller. That option let any account in the group sudo run a program of its choosing with root's rights, without a password. The present design fixes the interpreter's path in its gate, moves the decision about which accounts can give journals into the constraints, raises an error in the composer on a wrong argument where the first version dropped the operation silently, replaces a scope fence that the gate's change of directory made ineffective with constraints naming each file, removes temporary files after a failure, and gives a second backup within one second a name of its own.

Journal version 4 replaces version 3. In version 3 an instruction's arguments were a map by name, a value produced by an instruction was a symbol, the map {"symbol": <index>}, recognized by its shape, so that no argument could be a map, and each language wrote its own well-formed check. In version 4 a language is defined as data, a journal declares typed variables, an argument is a pair saying whether it is a literal or a variable, given by position, one well-formed guard serves every language, an instruction can write several variables, and a journal can have a result, handed back on descriptor 3. The composer directory is set aside until variables can be shared between composers.
